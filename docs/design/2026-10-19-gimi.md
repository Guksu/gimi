# gimi 설계

> 기미(氣味)상궁이 임금의 수라를 먼저 맛보듯, 코드를 올리기 전에 먼저 맛본다. 같은 소리의 기미(幾微)는 낌새라는 뜻이다. 문제의 기미를 diff 밖에서도 잡는다.

이 문서가 gimi 설계의 단일 출처다. 결정이 바뀌면 이 문서를 먼저 고친다.

## 1. 무엇을 해결하는가

AI 에이전트가 쓴 코드와 테스트에는 티가 난다. mock이 돌려준 값을 그대로 단언하는 테스트, 실패하자 기대값을 실제값으로 고친 테스트, `catch {}`로 삼킨 에러, `as any`, 실행하지 않고 "통과했어요"라고 하는 보고가 그렇다.

AI 리뷰에도 티가 난다. 지금의 리뷰 스킬은 그 커밋의 diff 안에서만 판단한다. 바뀐 함수를 쓰는 다른 화면, 티켓에 적힌 요구사항, 그 줄을 예전에 일부러 그렇게 둔 이유는 보지 않는다. 사람이 리뷰하며 잡는 결함은 대개 diff 밖에 있다.

gimi는 이 두 가지를 없앤다.

## 2. suta에서 가져오는 것

suta(UI의 AI 슬롭을 없애는 스킬, `Guksu/suta`)가 효과를 낸 장치를 그대로 쓴다.

| suta의 장치 | gimi에서 |
|---|---|
| "AI가 흔히 하는 것 / 대신 / 근거" 금지선 표 | 코드·테스트·리뷰 슬롭 금지선 |
| 정적 검사(`audit.mjs`) — `file:line` + 이유 + 고치는 법, 확실한 것만 error, 예외는 이유 주석 | 테스트·코드 슬롭 검사(`check.mjs`) |
| 하위 문서는 `PATTERN.md` — 스킬 목록에 따로 뜨지 않게 | 테스트 패턴, 분야 프리셋 |
| `@shared-core` 복사본 + 바이트 비교 | 두 스킬이 함께 읽는 규칙 |
| 선택 평가(트리거·패턴) — 문서보다 먼저 쓴다 | 두 스킬의 트리거 평가. decoy에 내장 `/code-review` 설명 포함 |
| 구조 검사(`validateSkills.mjs`) | 같은 방식 |
| 벤치마크 — 같은 요청을 있이·없이, 첫 실행으로 비교, 진 결과도 기록 | 리뷰 품질 측정(방법은 열린 질문) |
| 실사용 점검 루프 — 실제 프로젝트에 써 보고 규칙을 더한다 | 리뷰 지적 → 규칙 후보 → 사람 승인 → 규칙 |
| 한계 절 — "검사가 깨끗해도 끝난 것이 아니다" | 같은 방식 |

| 17 | 첫 분야 프리셋 | 커머스·결제. 결정 15의 예제 저장소도 커머스(국수집 주문 — suta 데모 테마를 잇는다) | 금액 계산·재고·쿠폰 중복·주문 상태 전이처럼 프론트엔드에서 자주 터지는 규칙이 많다 |
| 18 | 저장소 | GitHub 공개 `Guksu/gimi`, 기본 브랜치 `main`. 작업마다 브랜치를 따서 PR로 올리고, 머지는 사용자가 한다. 머지는 스쿼시만 허용하고(머지 커밋·리베이스 끔), 머지하면 브랜치를 지운다(GitHub 저장소 설정) | 포트폴리오 공개(결정 4). suta와 같은 작업 방식. `main`에 PR 하나가 커밋 하나로 남는다 |
| 19 | 맥락 수집 분담 | 모으는 건 스크립트(`context.mjs`), 판단은 에이전트 | diff만 보는 것이 AI 리뷰어의 습관이라, 수집을 에이전트 재량에 맡기면 같은 문제가 생긴다. 평가에서 수집 실패와 판단 실패를 나눌 수 있다. 결과가 매번 같아 테스트를 먼저 쓸 수 있다 |

| 22 | 이력 범위 | 바꾸거나 지운 줄의 blame + 파일마다 최근 커밋 N개(기본 10, 설정에서 조정) | 바꾸지 않은 주변 코드(같은 파일의 방어 코드 등)가 왜 생겼는지까지 본다. 늘어나는 소음은 요약의 순서·제외 규칙과 평가로 줄인다 |
| 23 | 스크립트 언어 | `.mjs`, 의존성 0, Node 22 이상 | 이 기기의 Node가 22.12라 suta의 `.ts` 스크립트(22.18 이상 필요)가 돌지 않는다. 같은 문제를 피한다 |
| 24 | 회사 저장소 파일 위치 | 설정은 `.agents/gimi.json`, 문서는 `docs/gimi/`(`rules.md`·`candidates.md`·`reviews/`) | guksu-harness와 같은 관례(설정은 `.agents/`, 기록은 `docs/`). 팀이 읽는 규칙과 기록은 눈에 보이는 곳에 둔다 |
| 25 | 설정 형식 | JSON | 의존성 없이 읽는다. YAML은 파서가 필요하다 |
| 26 | 회사 규칙 형식 | 규칙마다 절 + 고정 항목(왜·대신·확인·검사·근거), 제목에 ID. 규칙 후보는 같은 형식에 상태·출처를 더한다. 프리셋 규칙은 "끈 프리셋 규칙" 절에 이유와 함께 끈다 | 사람이 읽고 PR로 리뷰하기 쉽고, 스크립트도 항목을 읽는다. 표와 달리 긴 글과 정규식의 `\|`에 깨지지 않는다. ID가 있어야 지적·후보·끄기가 규칙을 가리킨다 |
| 27 | 리뷰 기록 | 리뷰마다 Markdown 하나가 정본. 지적마다 `규칙`·`판정` 항목을 둔다. 기록은 커밋하고, 맥락 묶음(`*.context.json`)은 `.gitignore`로 뺀다 | 팀 전체 기록으로 승격을 센다. 판정이 실사용 기록(결정 15②)이 된다. 맥락 묶음은 크고 다시 만들 수 있다. 판정을 JSON에 두면 사람이 고치기 불편하고, 둘 다 두면 어긋난다 |
| 28 | 테스트 패턴 1차 | 바탕 2개(`test-principles`·`test-audit`) + 1차 8개(`requirement-cases`·`domain-boundaries`·`regression-first`·`api-boundary`·`async-ui-states`·`user-interaction`·`race-and-duplicate`·`fake-time`). 2차 6개는 측정을 보고 순서를 정한다 | 우선순위 기준 ① gimi의 맥락·도메인과 이어지는가 ② 프론트엔드에서 자주 깨지는가 ③ AI가 자주 잘못 쓰는가. ③은 결정 16의 측정으로 다시 정렬한다 |
| 29 | 예시 기준 도구 | Vitest·Testing Library·user-event·MSW·Playwright. 패턴마다 Jest와 다른 줄만 표로 둔다 | 두 도구의 API가 거의 같다. 두 벌로 쓰면 함께 고쳐야 한다 |
| 30 | 예시 검증 | 패턴의 `assets/*.test.ts(x)`가 정본이다. `defects.mjs check`가 예제 저장소(결정 15)의 정상·결함 버전을 만들 때 그 파일을 워크스페이스에 복사해 돌린다(어디에 두고 어느 결함에 대는지는 `evals/patterns/{패턴}.json`). 좋은 예시는 결함 버전에서 실패하고, 슬롭 예시(`*.slop.test.ts(x)`)는 결함 버전에서도 통과하는 것을 확인한다 | 저장소에 복사본을 두지 않는다(suta 정본 원칙). "이렇게 쓰면 결함을 놓친다"를 말이 아니라 실행 결과로 보인다. 예제 저장소의 설정이 패턴 폴더를 직접 포함하면 정상 버전에 평가 흔적이 남고, 앱 밖 파일의 import 해석을 따로 맞춰야 한다(사용자 결정 2026-10-22 — 검사 때 복사) |
| 31 | React Native | 1차는 웹(React·Next). React Native는 2차 `react-native` 패턴에서 대응표로 옮긴다 | suta의 `react-native.md`와 같은 방식. 1차 패턴마다 확인할 것을 늘리지 않는다 |
| 32 | 공통 금지선 ID | `영역/이름`(예: `test/mock-echo`). 이름은 소문자·하이픈 | suta의 규칙 이름처럼 검사 출력과 예외 주석에서 무슨 규칙인지 바로 읽힌다. 회사 규칙(`SHOP-001`)·프리셋(`COM-001`)과 모양이 달라 섞이지 않는다 |
| 33 | 금지선 영역 | 4개 — `test`(테스트)·`code`(코드)·`review`(리뷰)·`done`(완료 보고) | 완료 보고는 끝내기 전(결정 7)이라는 다른 순간에 `check.mjs`가 잡는다 |
| 34 | 측정 뒤 남길 줄 | 결정 16의 측정에서 한 번 이상 나온 줄만 SKILL.md 금지선 표에 올리고 "N번 중 M번"을 단다. 나오지 않은 줄은 규칙 파일에만 두고 검사·리뷰에는 쓴다 | 표는 늘 읽히므로 근거가 있는 줄만 둔다(컨텍스트 절약). 측정 전에는 표에 올릴 줄이 없으므로 측정이 첫 릴리스보다 먼저 와야 한다 |
| 35 | 공통 규칙 파일 | ~~`shared/rules/frontend-ts/{test,code,review,done}.md`~~ → 경로는 결정 43에서 바뀜. 형식은 결정 26과 같고, `검사` 항목은 잡는 곳(error·warn·리뷰·기록)을 적는다. SKILL.md 표는 이 파일에서 만든다. 예외 주석은 `// gimi-ignore: {ID} — {이유}`이고, 이유가 없으면 무시한다 | 회사 규칙과 같은 형식이면 스크립트 하나로 읽는다. 표를 손으로 고치지 않는다(suta 카탈로그와 같다). error는 확실한 결함만(suta와 같다) |

- "모르는 상태 값에 예외"는 웹훅 재전송 폭주를 부른다 → 외부 값은 보류(COM-014).
- "결제 정보를 남기지 않는다"는 지나치다 → 가려서 남기고, PG가 요구하는 노티 로그는 남긴다(COM-027).
- 프론트 차단만으로는 근거가 부족하다 → 결제 한 번만·품절 차단에 서버 처리를 넣었다(COM-016·009).

## 5. 흐름 (초안)

### 처음 설정 — `gimi-review`

1. 분야 프리셋을 고른다(여러 개 가능).
2. 요구사항 출처를 고른다.
3. 코드에서 도메인 규칙 초안을 뽑아 `docs/gimi/candidates.md`에 후보로 쓴다 — enum·union 타입, 상태 전이 함수, 검증 스키마, 금액·날짜 계산 유틸. 출처는 `file:line`.
4. 사람이 승인한 후보만 `docs/gimi/rules.md`로 옮긴다.
5. 끝내기 전 검사를 이 프로젝트에 켤지 묻는다(결정 9).
6. 고른 값을 `.agents/gimi.json`에 쓰고, `.gitignore`에 `docs/gimi/reviews/*.context.json`을 더한다(아래 "회사 저장소의 파일").

### 리뷰 — `gimi-review`

1. 맥락을 모은다 — 스크립트가 맥락 묶음을 만들고, 에이전트가 그것을 읽어 판단한다(아래 "맥락 수집").
2. 금지선·분야 프리셋·회사 규칙과 대조한다.
3. 근거가 있는 지적만 보고한다(결정 12·13). 채팅에는 지적 수와 "고쳐야 함"만 짧게, 전체는 리뷰 기록 `docs/gimi/reviews/`에 쓴다(결정 14·27).
4. 규칙에 걸리지 않은 지적이 같은 묶음으로 `promoteAfter`번(기본 3) 쌓이면 `candidates.md`에 후보로 올린다. 판정이 틀림·의도함인 지적은 세지 않는다. 사람이 승인해야 규칙이 된다.

지적 하나의 형식:

```text
[고쳐야 함] 영향 범위
주문 상태 형태가 바뀌었는데 배지는 예전 형태를 읽는다

바뀐 곳  src/api/order.ts:42
         status: string → { code, label }
근거    src/components/OrderBadge.tsx:12
         status === 'PAID'  (이 PR에서 안 바뀜)
상황    결제 완료 주문 → 배지가 항상 '알 수 없음'
테스트  OrderBadge 테스트 없음
```

- 머리: 단계(고쳐야 함·고치면 좋음·확인 질문) + 맥락 종류(영향 범위·의도·이력·슬롭·도메인 규칙)
- `근거`는 diff 밖이어야 한다. 슬롭 지적만 예외로 diff 안의 줄을 근거로 쓴다.
- `확인 질문`은 상황 대신 "무엇이 어긋나 보이는가 + 의도했다면 무엇을 알려 달라"를 쓴다.

### 맥락 수집 — 스크립트가 모으고 에이전트가 판단한다 (결정 19~23)

| 맥락 | 스크립트(`context.mjs`)가 매번 모으는 것 | 에이전트가 판단하는 것 |
|---|---|---|
| 공통 | 리뷰 범위(PR 번호, 또는 현재 브랜치와 기본 브랜치의 갈림점), 바뀐 파일·줄 | 어느 범위를 볼지 사용자와 확인 |
| 영향 범위 | 바뀐 export와 그 종류(추가·삭제·시그니처 변경·본문만 변경), 사용처 `file:line` + 앞뒤 2줄, 그 사용처가 이 PR에서 함께 바뀌었는지. 지우거나 바꾼 문자열(쿼리 키·라우트 경로·i18n 키·저장소 키)이 쓰이는 다른 곳 | 사용처가 의미상 깨지는지. 필요하면 2단계 이상 따라간다 |
| 의도·요구사항 | PR 제목·본문, 커밋 메시지, 브랜치 이름, 티켓 번호·링크(`SHOP-123` 등), 연결된 GitHub 이슈 본문(`gh pr view --json closingIssuesReferences`) | 외부 출처 본문을 MCP 연결로 읽는다(없으면 붙여 넣기 요청). 요구사항을 항목으로 쪼개 diff와 대조해, 빠진 것과 요청하지 않은 동작 변경을 찾는다 |
| 변경 이력 | 바꾸거나 지운 줄의 blame, 파일마다 최근 커밋 N개(기본 10). 커밋마다 제목·본문·연결 PR. 수정·되돌리기·우회 커밋(fix·revert·hotfix·workaround)을 표시하고, 서식 정리 커밋은 뺀다(`.git-blame-ignore-revs`를 따른다) | 새 변경이 예전 수정을 되돌리거나 건너뛰는지 판단해 "확인 질문"으로 올린다 |
| 출력 | 전체는 JSON 파일, 에이전트에게는 상한이 있는 요약. 못 모은 것은 이유와 함께 "건너뜀" | 건너뛴 맥락이 있으면 보고에 적는다 |

**사용처 찾기(결정 20).** 프로젝트 `node_modules`의 `typescript`를 불러와 언어 서비스의 참조 찾기를 쓴다. 바뀐 export는 바뀐 줄을 감싼 최상위 선언을 옛 파일·새 파일에서 각각 찾아 비교해 종류를 정한다. 본문만 바뀌어도 사용처는 모은다(의미가 바뀌었을 수 있다). 다만 요약에서는 시그니처 변경보다 뒤에 둔다.

**건너뜀의 예.** gh 로그인이 없으면 PR·이슈 본문을 건너뛴다. 얕은 복제(CI의 `fetch-depth: 1`)에서는 이력을 건너뛴다. `typescript`가 없으면 문자열 검색으로 내려간다. 어떤 경우든 "없음"과 "건너뜀"을 구분한다. 사용처를 찾지 못한 것과 찾기를 건너뛴 것은 다르다.

**계약 파일의 영향 범위(3단계 구현).**

- **OpenAPI.** 바뀐 YAML·JSON 가운데 `openapi`·`swagger` 키가 있는 문서를 옛 판·새 판으로 비교한다(3.x·Swagger 2.0). 비교하는 것은 엔드포인트(메서드 + 경로), 파라미터, 요청 본문, 응답 코드와 응답 스키마, 스키마 필드(타입·null 허용·필수·enum)다. 바뀐 스키마를 쓰는 엔드포인트는 `$ref`를 따라가 찾는다. 다른 파일을 가리키는 `$ref`는 따라가지 않는다.
- **YAML 읽기(사용자 결정).** 리뷰하는 프로젝트의 `yaml`·`js-yaml`을 먼저 쓰고, 없으면 내장 최소 파서로 읽는다. 내장 파서는 OpenAPI에 흔한 문법만 읽고, 앵커·별칭·태그·복합 키·탭 들여쓰기·여러 문서를 만나면 틀리게 읽지 않고 건너뜀으로 적는다. Petstore식 문서에서 js-yaml과 결과가 같다.
- **OpenAPI 사용처(사용자 결정).** 바뀐 엔드포인트와 필드가 바뀐 스키마를 쓰는 엔드포인트의 경로를 문자열로 찾는다. 찾는 문자열은 경로 그대로와 경로 변수 앞까지(`/orders/{id}` → `/orders/`)다. 생성 타입(openapi-typescript·orval·OpenAPI Generator·swagger-typescript-api)이 있으면 바뀐 스키마·필드 선언을 찾아 TypeScript 참조로도 찾는다. TypeScript는 중첩 생성 타입(`components["schemas"]["Order"]`)의 필드 사용처는 찾지만, 경로 키를 문자열로 넘기는 호출(`GET('/orders/{id}')`)은 찾지 못한다. 그래서 엔드포인트는 생성 타입이 있어도 문자열로 찾는다.
- **GraphQL(사용자 결정).** 저장소의 스키마 파일(`.graphql`·`.graphqls`·`.gql` 가운데 타입 정의가 있는 것)을 모두 합쳐 옛 판·새 판을 비교한다. 비교하는 것은 타입·필드·인자·enum 값·union 멤버·input 필드다. 출력 필드는 null 허용이 되면 확인이고, 입력(인자·input 필드)은 필수가 되면 깨질 수 있음이다. 사용처는 코드 안의 연산(gql·graphql 태그 템플릿, ``graphql(`…`)``, `/* GraphQL */` 템플릿, 스키마가 아닌 `.graphql` 파일)을 스키마로 풀어 찾는다. 선택 집합을 스키마로 따라가 필드마다 부모 타입을 정하므로 이름이 같은 다른 타입의 필드와 섞이지 않는다. 지운 필드는 옛 스키마로 푼다. enum·input이 바뀌면 그것을 돌려주거나 (중첩 input까지) 인자로 받는 필드가 대상이다. Expo의 실제 스키마(타입 690개)와 연산으로 확인했다.
- **공통.** 더하기만 한 변경은 아직 쓰는 곳이 없으니 찾지 않는다. 깨질 수 있음·확인부터 계약마다 20개까지 찾는다. 계약은 바뀌었는데 생성 타입이 이 변경에서 바뀌지 않았으면 "다시 생성했는지 확인한다"를 참고에 적는다. proto는 건너뜀에, 서버 코드 안의 GraphQL 스키마(gql typeDefs)는 참고에 적는다(아직 읽지 않는다).

### 테스트 패턴 (결정 28~31)

suta의 패턴이 "UI를 이렇게 만든다"라면, gimi-test의 패턴은 "이런 상황은 이렇게 테스트한다"다.

| 순위 | 패턴 | 무엇을 | AI가 흔히 하는 것 |
|---|---|---|---|
| 바탕 | `test-principles` | 무엇을 테스트할지, 테스트 더블(mock·fake·실물) 고르는 기준, 이름, 파일 위치 | 모든 import를 mock한다 |
| 바탕 | `test-audit` | `check.mjs`가 쓰는 테스트 슬롭 규칙표 | — |
| 1차 | `requirement-cases` | 티켓·PR의 요구사항 항목 → 테스트 이름 1:1, 빠진 항목 표시 | 요구사항이 아니라 구현을 따라 테스트를 쓴다 |
| 1차 | `domain-boundaries` | 회사 규칙·프리셋 규칙마다 경계값 표(`it.each`). 예: 0원, 최소 주문 금액 경계, 재고 0·1, 쿠폰 중복 | 정상값 하나만 넣어 본다 |
| 1차 | `regression-first` | 버그 수정은 재현 테스트부터 쓰고, 수정 전 코드에서 실패하는지 확인 | 고친 뒤에 통과하는 테스트만 쓴다 |
| 1차 | `api-boundary` | MSW 핸들러로 성공·4xx·5xx·네트워크 끊김·느린 응답 | `fetch`·axios 모듈을 mock하고 그 mock을 단언한다 |
| 1차 | `async-ui-states` | 로딩 → 성공·빈 상태·오류를 상태마다 하나씩 | `waitFor` 안에서 아무거나 기다리거나 시간을 늘린다 |
| 1차 | `user-interaction` | user-event로 사용자처럼 조작하고 `getByRole` + 이름으로 찾기, 폼 제출·검증 | state·클래스명·내부 함수 호출을 단언한다 |
| 1차 | `race-and-duplicate` | 연타 → 요청 1번, 늦게 온 응답 무시, 언마운트 뒤 응답 | 정상 순서 하나만 확인한다 |
| 1차 | `fake-time` | debounce·폴링·만료·카운트다운, 날짜·타임존 고정 | 실제로 `setTimeout`을 기다리거나 현재 시각에 기대어 가끔 깨진다 |
| 2차 | `state-transition` | 상태 전이를 허용·금지 쌍 표로 | 성공 경로 하나만 따라간다 |
| 2차 | `query-cache` | React Query·SWR 캐시, 무효화, 낙관적 갱신 되돌리기 | 테스트끼리 캐시를 공유해 순서에 따라 결과가 바뀐다 |
| 2차 | `keyboard-focus` | 키보드 조작, 포커스 이동·복귀, Esc | 클릭만 테스트한다 |
| 2차 | `e2e-journey` | Playwright로 핵심 사용자 흐름 3~5개 | 모든 화면을 e2e로 덮어 느리고 잘 깨진다 |

| 2차 | `react-native` | React Native Testing Library에 맞춰 옮기기 | 웹 쿼리를 그대로 쓴다 |

**백엔드 패턴(결정 48).** 위 표의 바탕 2개와 `requirement-cases`·`domain-boundaries`·`regression-first`는 언어와 상관없어 대상이 둘 다다. 나머지는 프론트 패턴이다.

| 순위 | 패턴 | 무엇을 | AI가 흔히 하는 것 |
|---|---|---|---|
| 1차 | `concurrency` | 재고 1에 동시 N건, 같은 쿠폰 동시 사용 → 성공 1건 | 순차 호출 두 번으로 끝낸다 |
| 1차 | `idempotency` | 같은 멱등 키 재시도, 같은 결제 확정 두 번 → 부수효과 1번 | 한 번 호출만 본다 |
| 1차 | `webhook-contract` | 서명 틀림, 같은 이벤트 두 번, 역순 도착, 모르는 type | 정상 이벤트 하나만 보낸다 |
| 1차 | `external-api-fake` | PG 등 외부 API를 HTTP 가짜 서버로(성공·4xx·5xx·타임아웃) | HTTP 클라이언트 모듈을 mock한다 |
| 1차 | `db-integration` | 실제 DB로 저장소·제약(유니크·외래키) 테스트, 테스트마다 격리 | 저장소를 mock한다 |
| 1차 | `api-contract` | 응답 형태를 계약 파일과 대조(결정 47의 API 경계와 맞물림) | 상태 코드만 본다 |
| 2차 | `transaction-boundary` | 실패하면 롤백, 외부 호출은 커밋 뒤 | 성공 경로만 본다 |
| 2차 | `migration` | 데이터가 있는 상태에서 마이그레이션 올리기·내리기 | 빈 DB에서만 돌린다 |
| 2차 | `scheduled-job` | 만료·배치를 가짜 시계로(`fake-time`의 백엔드판) | 실제 시간을 기다린다 |

`e2e-journey`는 guksu-harness `fe-predeploy`와 다르다. predeploy는 배포 전에 브라우저에서 계측하고, 이 패턴은 저장소에 남길 테스트를 쓰는 법이다.

**PATTERN.md 본문 순서.** 언제 쓰는가 → 무엇을 단언하는가 → 예시(`assets/`) → "AI가 흔히 쓰는 테스트 / 대신" 표 → Jest와 다른 줄 → 주의사항. 패턴마다 `evals/selection/{패턴}.json`을 문서보다 먼저 쓴다(suta와 같다).

이 표가 깨지면 패턴이 틀린 것이다. 좋은 예시가 결함 버전에서 통과하면 결함을 못 잡는 예시이고, 슬롭 예시가 결함 버전에서 실패하면 슬롭이라고 부를 근거가 없다.

**구현(테스트 패턴 1단계).**

**구현(테스트 패턴 — 맥락 결함).**
- `requirement-cases`·`regression-first`는 의도·이력 결함과 짝이다. 사용자 요청("남은것들도 각각 진행해서 pr올려줘")에 따라 묶음마다 PR을 따로 올린다.

- 이력 결함 HIST-001(규칙 COM-012) — `defect.json`의 `history`로 평가용 저장소의 `main`에 "fix: 새벽에 받은 주문의 반품 기한이 하루 짧던 문제" 커밋을 쌓는다. 결함 PR은 그 수정의 한국 시간 처리를 "한 줄로 정리"하며 지운다. 맥락 수집의 이력(바뀐 줄을 넣은 커밋)으로 찾을 수 있는 결함이다.
- `history` 형식(제가 정함) — 커밋마다 메시지와 `history/` 아래의 패치(그 커밋 앞 → 뒤). `materialize`가 정상 버전에서 패치를 거꾸로 풀어 처음 상태를 커밋하고 다시 올린다. `main`의 마지막 상태는 늘 정상 버전과 같아, 잡는 테스트·패턴 예시 검증은 그대로다.
- 수정 전 코드는 "날짜를 구한 뒤에만 오프셋을 뺀" 실수로 두어, 새벽 배송만 하루 이르다. 그래서 정상 버전의 다른 반품 테스트(낮 배송)는 수정 전 코드에서도 통과하고, 수정 커밋이 더한 재현 테스트만 실패한다.
**구현(테스트 패턴 — 바탕).**
- 바탕 2개를 더했다. 사용자 요청("남은것들도 각각 진행해서 pr올려줘")에 따라 묶음마다 PR을 따로 올린다.

- `test-audit` — 테스트 금지선 21줄을 잡는 곳(check.mjs의 error·warn, 리뷰)과 함께 한 표로 보인다. 예시는 결함 버전이 아니라 `check.mjs`로 검증한다(제가 정함). 슬롭 예시를 `cart.test.tsx`로 두면 검사 규칙 14개를 찾고, 좋은 예시는 아무것도 찾지 않는다. `tests/pattern-assets.test.mjs`가 규칙표와 규칙 파일의 "검사"가 같은지도 본다.
- 같은 테스트가 모든 패턴의 좋은 예시에 `check.mjs` 지적이 없는지 본다. 사용자가 복사해 쓸 정본이기 때문이다. 다른 패턴의 슬롭 예시는 이 검사를 통과한다. 정규식으로 못 잡고 결함 버전에서만 드러나는 슬롭이다.

**구현(예제 저장소 단계).**

- 스택은 web React 19 + Vite, server NestJS 11 + pg(SQL을 직접 쓴다), fake-pg(`node:http`, 의존성 0)이고 모두 TypeScript + Vitest다. 사용자 결정 — Express 대신 NestJS. npm 워크스페이스로 묶고 의존성은 예제 저장소의 `package-lock.json`에만 둔다(gimi 루트는 런타임 의존성 0을 지킨다).
- 정상 버전은 프리셋을 지킨다 — 금액은 서버가 다시 계산하고 저장값만 PG에 보낸다, 재고·쿠폰·포인트는 조건부 UPDATE, 멱등 키는 화면 하나에 하나, 결제 완료는 PG 조회로 확정, 웹훅은 서명 검증 + 이벤트 ID로 중복 제거, 상태는 전이표로만 바꾼다, 반품 기한은 `returnDeadline` 한 곳에서. 테스트는 fake-pg 7·server 49·web 21개다.
- 결함 PR은 `defects/{ID}/change.patch` + `defect.json`이다(사용자 결정 — 패치 + 정답 파일). `defect.json`은 어긴 규칙·맥락 종류·층·PR 제목과 본문·정답(단계 + `path:line`~`endLine` + 근거 위치)·잡는 테스트를 적는다. 형식은 `evals/shop-fixture/defects/README.md`다.
- `scripts/defects.mjs`(판단은 `scripts/lib/defects.mjs`)가 다룬다. `materialize <ID> <폴더>`는 평가용 git 저장소를 만든다 — `main` = 정상 버전(예제 저장소에서 `defects/`를 뺀 것), `defect/<ID>` = PR 제목·본문을 메시지로 한 결함 커밋. 작성자·시각을 고정해 커밋 해시가 늘 같다. `check`는 패치가 붙는지, 형식, 정답 위치가 결함 버전에 있는지, 잡는 테스트가 정상 버전에서 통과하고 결함 버전에서 실패하는지 본다.
- CI는 매 PR에 별도 job으로 PostgreSQL 서비스 컨테이너를 띄워 타입 검사·앱 테스트·`defects.mjs check`를 돌린다(사용자 결정). 정상 버전을 고쳐 패치가 붙지 않으면 이 job이 실패한다.
- 첫 결함은 셋이다 — COM-007(백엔드, 재고를 읽고 앱에서 비교해 덮어쓴다), COM-016(프론트, 누를 때마다 새 멱등 키), KCL-001(법령, 반품 기한을 배송 시각 + 7×24시간으로 따로 계산). 사용자 결정 — 앱 + 도구 + 예시 3개. 나머지 프리셋 규칙의 결함 PR은 묶음 PR로 더한다.
- 결함 PR은 정상 버전의 테스트를 통과하지 않아도 된다(사용자 결정 2026-10-22 — 평가용이다). 지금의 세 결함은 정상 버전의 테스트가 잡는다. 리뷰 평가는 diff와 맥락만 보므로 채점에 영향이 없다. 이력 결함은 `history`(예전 커밋)로 평가용 저장소의 `main`에 커밋을 쌓는다(위의 '구현(테스트 패턴 — 맥락 결함)').

### 끝내기 전 — `gimi-test`

`check.mjs`가 바뀐 범위의 테스트·타입 검사를 실제로 돌리고, 테스트·코드 슬롭을 검사한다. 보고에는 실행한 명령과 결과를 붙인다. 실행하지 못한 검사는 이유와 함께 "건너뜀"으로 적는다.

**명령 찾기(결정 50).** 아래 순서로 찾는다.

1. 설정 `finishCheck.commands`
2. guksu-harness verifier 설정(`.agents/hooks/verifierGate.config.json`)
3. 프로젝트 파일 감지:

| 파일 | 테스트(바뀐 범위) | 타입 검사 |
|---|---|---|
| `package.json` | `vitest related <파일>`·`jest --findRelatedTests <파일>`, 없으면 scripts의 `test` | `tsc --noEmit`(또는 scripts의 typecheck) |
| `build.gradle(.kts)` | `./gradlew :{모듈}:test` | `./gradlew :{모듈}:compileKotlin`·`compileJava` |
| `pom.xml` | `mvn -pl {모듈} test` | `mvn -pl {모듈} compile` |
| `pyproject.toml` | `pytest {바뀐 테스트·패키지}` | `mypy`(설정이 있을 때) |
| `go.mod` | `go test ./{패키지}/...` | `go vet ./{패키지}/...` |

바뀐 파일이 속한 패키지·모듈만 돌린다. 어디서도 찾지 못하면 "건너뜀 + 이유"로 적는다(`done/skipped-checks`).

**슬롭 정적 검사(7절의 "검사 error·warn" 줄).** 2단계에서 구현했다.

- **범위.** 갈림점과 작업 트리를 비교한 바뀐 줄만 본다. 추적하지 않는 새 파일은 모든 줄을 본다. "단언 없는 테스트"처럼 블록 단위 지적은 블록 안의 줄이 하나라도 바뀌면 알린다.
- **파일.** JS·TS 파일만 본다. 타입 선언·압축 파일·점 폴더·1MB 넘는 파일은 뺀다. 테스트 파일은 이름(`.test`·`.spec`), 테스트 폴더(`__tests__`·`__mocks__`·`test`·`tests`), 테스트 설정(`jest.setup`·`setupTests`)으로 가른다. 스냅샷(`.snap`)은 고쳤는지만 본다.
- **읽는 방법.** 파서 대신 토큰 읽기를 쓴다. 주석·문자열·정규식 리터럴을 가리고 괄호 짝을 맞춰 정규식으로 찾는다. 런타임 의존성 0을 지키고, TypeScript 7처럼 언어 서비스 API가 없는 버전에서도 같게 동작한다. 그래서 다른 파일의 도우미 안은 볼 수 없다. 테스트 도우미 모듈에서 가져온 함수를 부르는 테스트는 "단언 없음"으로 판단하지 않는다.
- **등급.** error가 있으면 종료 코드 1이다. warn만 있으면 0이고, 보고에 고치거나 이유를 적으라고 쓴다. 건너뛰게 한 테스트·바꾼 기대값·갱신한 스냅샷은 `done/test-bent`로 보고에 밝히라고 쓴다.
- **무시.** 줄 끝이나 바로 윗줄의 `// gimi-ignore: {ID} — {이유}`로 무시한다. 이유가 없으면 무시하지 않고 그렇다고 적는다.
- **프론트 전용 줄**(`test/implementation-detail`·`test/waitfor-misuse`·`test/testid-first`·`code/index-key`)은 설정 `stacks`에 `frontend-ts`가 있을 때만 본다.

**오탐 보정(muklog — 테스트 249·코드 479개, 1,487건 → 43건).** 실제 저장소에 돌려 아래를 뺐다.

| 무엇 | 왜 뺐나 |
|---|---|
| `expect(getByTestId(…)).toBeTruthy()` | React Native의 관용구다. 조회가 이미 있는지 확인하므로 늘 참인 단언이 아니다. `render(…)` 결과의 `toBeTruthy`만 `test/tautology`로 본다 |
| `@testing-library/react-native`의 testID 찾기 | React Native는 testID가 관례다(React Native는 2차 범위) |
| `.catch(() => null)` | 실패를 대체값으로 바꾸는 처리다. `() => {}`처럼 비어 있을 때만 `code/empty-catch`로 본다 |
| `expect(f(x)).toBe(f(x))`·`.not.toBe(f())` | 결정성 확인(같은 입력 → 같은 값, 두 번 → 다른 값)이다. 호출이 없는 같은 식만 늘 참으로 본다 |
| if 밖에도 단언이 있는 테스트의 if 안 단언 | 조건이 거짓이어도 무언가는 확인한다. 단언이 모두 if 안에 있을 때만 `test/swallowed-failure`로 본다. if 안의 getBy 조회는 단언으로 치지 않는다 |
| `globalThis.fetch = originalFetch` | 원래 fetch로 되돌리는 대입이다 |
| 문장 속 "localhost" | 주소 모양(`http://localhost`·`localhost:포트`)일 때만 본다 |

`code/debug-leftover`가 guksu-harness `fe-predeploy` 정적 스캔과 겹치는 문제는 범위로 가른다. gimi는 이 변경의 바뀐 줄만 보고, `fe-predeploy`는 배포 전 전체를 본다.

**기준 비교(`--baseline`, `done/blamed-preexisting`).** 3단계에서 구현했다.

- 실패·시간 초과한 명령만 갈림점의 코드에서 다시 돌린다. `git archive`로 갈림점의 추적 파일을 임시 폴더에 푼다. git 객체를 읽기만 해서 저장소·작업 트리·브랜치를 건드리지 않는다. 임시 폴더는 끝나면 지운다.
- 의존성은 다시 설치하지 않는다. 저장소 루트와 검사 폴더의 `node_modules`를 링크한다. 의존성 파일(`package.json`·잠금 파일)이 바뀐 변경이면 그렇다고 밝힌다.
- 프로젝트 파일로 찾은 명령은 기준에 있는 파일로 다시 계획한다. 관련 테스트에 넘긴 새 파일은 기준에 없기 때문이다. 볼 파일이 하나도 없으면 이 변경에서 생긴 실패로 적는다.
- 판정은 넷이다. 기준에서는 통과(이 변경에서 생김), 기준에서도 실패(원래 있던 실패일 수 있음, 기준 출력 끝을 함께 보인다), 실패 수가 늘어남(n → m), 기준에서 돌리지 못함. 종료 코드는 기준 결과와 상관없이 그대로다.
- 임시 폴더는 git 저장소가 아니다. git이 필요한 명령은 기준에서 실패할 수 있다(사용자 결정 — worktree는 `.git/worktrees`에 기록을 남긴다).

**옵트인 연결(결정 9, `connect.mjs`).** 3단계에서 구현했다.

- `check.mjs`와 `lib/`를 프로젝트의 `.agents/gimi/check/`에 복사한다(사용자 결정). 커밋하면 gimi를 설치하지 않은 팀원에게도 돌고, 등록 명령은 상대 경로가 된다. guksu-harness가 훅을 `.agents/hooks/`에 복사하는 방식과 같다. 복사한 파일의 해시를 `manifest.json`에 남긴다. 다시 연결하면 지난 복사본 그대로인 파일만 새 판으로 바꾸고, 손으로 고친 파일은 충돌로 남긴다.
- `.agents/gimi.json`의 `finishCheck.enabled`를 켠다. 훅·verifier 모드는 이 값이 true일 때만 돈다.
- guksu-harness verifier(`.agents/hooks/verifierGate.mjs`, v2는 `.claude/hooks/`)가 있으면 그 설정에 `check.mjs --verifier` 항목을 더한다. 이 모드는 하네스가 직접 돌리는 명령을 다시 돌리지 않고 슬롭 검사만 한다(사용자 결정 — "무엇을 검사할지"만 제공). 하네스에 gimi 항목만 있으면 gimi가 찾은 명령도 돌린다. 하네스는 검사 하나를 5분에서 끊으므로 명령마다 2분이 기본 상한이다.
- 하네스가 없으면 Stop 훅에 `check.mjs --hook`을 등록한다. Claude Code는 `.claude/settings.json`(시간 상한 900초), Codex는 `.codex/hooks.json`이다. 앱은 `--app`으로 정하고, 생략하면 guksu-harness와 같은 신호(`.claude/`·`CLAUDE.md` / `.codex/`·`AGENTS.md`·`.agents/skills`)로 추정한다(사용자 결정).
- Stop 훅은 세션마다 상태를 임시 폴더에 둔다(저장소에 쓰지 않는다). 마지막으로 통과한 뒤 바뀐 것이 없으면 다시 돌리지 않는다. 지문은 갈림점 diff와 새 파일의 크기·수정 시각이다. 실패하면 종료 코드 2와 보고로 막는다. 사용자 메시지 뒤 첫 Stop이면 막은 횟수를 새로 센다.
- 끝없이 막지 않는다. 막은 뒤 아무것도 바꾸지 않고 끝내려 하거나, 같은 차례에 3번 넘게 막거나(`finishCheck.maxBlocks`), 같은 실패가 3번 이어지면(`finishCheck.stuckAfter`) "보고하고 끝낸다"고 한 번 막은 뒤 끝내게 둔다.
- `--remove`는 등록한 항목만 떼고, 고치지 않은 복사본을 지우고, 설정을 끈다.
- 검사가 멈추라는 신호(SIGTERM·SIGINT)를 받으면 돌고 있는 명령의 프로세스 그룹까지 멈춘다. verifier가 시간 초과로 끊어도 테스트 프로세스가 남지 않는다.

## 6. 회사 저장소의 파일 (결정 24~27)

```text
.agents/
  gimi.json                         설정
docs/gimi/
  rules.md                          회사 규칙 — 정본
  candidates.md                     규칙 후보 — 승인 대기·거절
  reviews/
    2026-10-19-pr-42.md             리뷰 기록 — 커밋한다
    2026-10-19-pr-42.context.json   맥락 묶음 — .gitignore
```

세 Markdown 파일은 같은 방식으로 쓴다. 항목 하나가 `##` 절 하나이고, 절 안에 정해진 항목을 `- 이름: 값`으로 적는다. 사람은 그대로 읽고, 스크립트는 절과 항목을 읽는다.

### 설정 — `.agents/gimi.json`

```json
{
  "stacks": ["frontend-ts", "backend"],
  "presets": ["commerce", "kr-commerce-law"],
  "kcl": { "periodCounting": "civil-code", "businessDays": "docs/gimi/business-days.json" },
  "requirements": [{ "source": "github" }, { "source": "jira", "keyPattern": "SHOP-\\d+" }],
  "rulePrefix": "SHOP",
  "history": { "recentCommits": 10 },
  "promoteAfter": 3,
  "finishCheck": { "enabled": true }
}
```

| 항목 | 뜻 | 기본값 |
|---|---|---|
| `stacks` | 슬롭 규칙·테스트 패턴의 대상(여러 개 — 결정 36·43). 값은 `frontend-ts`·`backend` | `["frontend-ts"]` |
| `presets` | 분야 프리셋(여러 개 — 결정 39) | `[]` |
| `kcl.periodCounting`·`kcl.businessDays` | `kr-commerce-law`의 해석 값 — 청약철회 기간 계산 방식, 영업일 달력(결정 42) | 없음 — 리뷰가 확인 질문으로 올린다 |
| `requirements` | 요구사항 출처와 티켓 번호 형식(결정 10·21) | `[{ "source": "github" }]` |
| `rulePrefix` | 회사 규칙 ID의 머리 | `"TEAM"` |
| `history.recentCommits` | 파일마다 볼 최근 커밋 수(결정 22) | `10` |
| `promoteAfter` | 같은 묶음의 지적이 몇 번 쌓이면 후보로 올릴지 | `3` |
| `finishCheck.enabled` | 이 프로젝트에서 끝내기 전 검사를 자동으로 돌릴지(결정 9). `connect.mjs`가 켜고, Stop 훅·verifier 모드는 true일 때만 돈다 | `false` |
| `finishCheck.commands` | 끝내기 전에 돌릴 명령(결정 50 — 있으면 이것만 돌린다) | 없음 |
| `finishCheck.maxBlocks`·`finishCheck.stuckAfter` | Stop 훅이 같은 차례에 막는 최대 횟수, 같은 실패가 몇 번 이어지면 보고하고 끝내게 할지 | `3`·`3` |

검증 명령은 결정 50의 순서(설정 `finishCheck.commands` → guksu-harness verifier → 프로젝트 파일)로 찾는다. 다르게 돌려야 하면 `finishCheck.commands`에 적는다.

### 회사 규칙 — `docs/gimi/rules.md`

```markdown
## SHOP-001 금액은 정수 원 단위로만 계산한다
- 왜: 부동소수 오차로 결제액이 1원 어긋났다(#412)
- 대신: toWon()으로 정수화한 뒤 계산한다
- 확인: 영향 범위 — price·amount의 곱셈·나눗셈
- 검사: /(price|amount)\s*\*\s*0\.\d+/
- 근거: 리뷰 3건에서 승격, 2026-10-12 승인

## 끈 프리셋 규칙
- COM-004 — 쿠폰 중복은 서버에서만 막는다
```

- 제목은 `## {ID} {한 줄 규칙}`이다. ID는 `{rulePrefix}-{세 자리}`이고, 규칙을 지워도 번호를 다시 쓰지 않는다. 옛 리뷰 기록이 그 번호를 가리키기 때문이다.
- `왜`·`대신`·`확인`은 필수다. `검사`(정규식 — 스크립트가 바뀐 줄에서 찾는다)와 `근거`는 선택이다.
- 프리셋 규칙은 "끈 프리셋 규칙" 절에 ID와 이유를 적어 끈다. 이유가 없는 줄은 무시하고 경고한다.
- 프리셋 ID는 분야 머리를 쓴다(`commerce`는 `COM-`, `kr-commerce-law`는 `KCL-`). 공통 금지선은 `영역/이름`이다(결정 32).
- 프리셋 규칙은 `대상`·`경계값`을 더한다(결정 40). 회사 규칙에도 선택 항목으로 쓸 수 있다.

### 규칙 후보 — `docs/gimi/candidates.md`

```markdown
## SHOP-007 주문 상태는 orderMachine.ts에서만 바꾼다
- 상태: 대기
- 출처: 리뷰 3건 — reviews/2026-10-02-pr-31.md#2, reviews/2026-10-09-pr-35.md#1, reviews/2026-10-15-pr-40.md#3
- 왜: 화면마다 상태 전이를 따로 하면 결제 취소 후에도 배송 준비로 넘어간다
- 대신: orderMachine.transition()을 부른다
- 확인: 영향 범위 — setStatus·status 대입
```

- 회사 규칙과 같은 형식에 `상태`(대기·거절)와 `출처`를 더한다. 출처는 코드 추출이면 `file:line`, 승격이면 리뷰 기록의 지적 링크다.
- 사람이 채팅에서 승인하면 에이전트가 `rules.md`로 옮긴다. 출처는 `근거` 항목에 남기고 후보에서는 지운다.
- 거절하면 `상태: 거절 — {이유}`로 남긴다. 같은 묶음은 다시 후보로 올리지 않는다.

### 리뷰 기록 — `docs/gimi/reviews/{날짜}-pr-{번호}.md`

PR이 없으면 `{날짜}-{브랜치}.md`로 쓴다.

```markdown
# 리뷰 — PR #42 주문 상태 표시 개선

- 날짜: 2026-10-19
- 범위: main...feat/order-status (커밋 3, 파일 7)
- 맥락: 영향 범위 export 3·사용처 9 / 의도 PR #42·이슈 #38·SHOP-123 / 이력 커밋 12 / 건너뜀 없음
- 결과: 고쳐야 함 1 · 고치면 좋음 2 · 확인 질문 1

## 1. [고쳐야 함] 영향 범위 — 주문 상태 형태가 바뀌었는데 배지는 예전 형태를 읽는다
- 바뀐 곳: `src/api/order.ts:42` — status: string → { code, label }
- 근거: `src/components/OrderBadge.tsx:12` — status === 'PAID' (이 PR에서 안 바뀜)
- 상황: 결제 완료 주문 → 배지가 항상 '알 수 없음'
- 테스트: OrderBadge 테스트 없음
- 규칙: 없음 — 묶음 `api-shape-consumer`
- 판정: 미정
```

- 지적의 항목은 결정 12의 형식과 같다. 채팅에서는 줄 맞춘 글로, 기록에서는 `- 이름: 값`으로 쓴다.
- `규칙`은 걸린 규칙의 ID(공통 금지선·`COM-`·회사 규칙)를 적는다. 걸린 규칙이 없으면 `없음 — 묶음 {짧은 이름}`을 적는다. 승격 집계는 규칙이 없는 지적을 묶음 이름으로 센다.
- `판정`은 미정·맞음·틀림·의도함 중 하나다. 사용자가 채팅으로 알려 주면 에이전트가 고치고, 사람이 파일을 직접 고쳐도 된다. 실사용 기록(결정 15②)의 찾은 비율과 오탐 비율은 이 항목으로 센다.

## 7. 슬롭 금지선 초안 (결정 32~35)

아래 61줄(프론트·공통 43 + 백엔드 18)은 모두 측정 전의 가설이다. 결정 16·49의 측정(같은 요청을 gimi 없이 실행)에서 나온 줄만 SKILL.md 표에 올라간다(결정 34).

측정 요청문의 주제(결정 49, 문구는 열린 질문 7):

- 프론트 6개 — 상품 목록 필터·정렬, 장바구니 수량 변경, 쿠폰 입력, 결제 완료 화면, 주문 내역 상태 표시, 장바구니 합계 테스트 작성
- 백엔드 6개 — 주문 생성 API, 결제 승인 처리, 결제 웹훅, 재고 차감, 부분 환불, 쿠폰 사용 API 테스트 작성

잡는 곳:

- **검사 error** — `check.mjs`가 막는다. 확실한 결함만 둔다.
- **검사 warn** — 알리고 판단은 맡긴다.
- **리뷰** — gimi-review가 맥락을 보고 판단한다.
- **기록 검사** — 리뷰 기록 파일의 형식에서 잡는다(근거 위치가 diff 안인지, 건너뛴 맥락에 기댄 지적인지).

### 규칙 파일 (결정 35·43)

```text
skills/{gimi-review,gimi-test}/shared/rules/   @shared 복사본 (원본은 하나)
  test.md     test/*
```

```markdown
## test/mock-echo mock이 돌려준 값을 그대로 단언하지 않는다
- 대상: 둘 다
- 왜: 대상 코드가 틀려도 통과한다
- 대신: 입력 → 출력·부수효과를 단언한다
- 확인: 같은 테스트 안에서 mockReturnValue·mockResolvedValue에 넣은 값과 expect의 기대값이 같다
- 검사: warn
- 근거: 측정 전
```

- `검사`는 잡는 곳(error·warn·리뷰·기록)이다. 실제 검사는 `check.mjs`의 코드가 한다. 회사 규칙의 `검사`(정규식)와 뜻이 다르다.
- `근거`는 측정 뒤 "기능 구현·테스트 작성 요청 N번 중 M번"으로 바뀐다. 한 번 이상 나온 줄만 SKILL.md 표에 올라간다.
- `대상`은 프론트·백엔드·둘 다 중 하나다. 스크립트가 설정의 `stacks`로 걸러 에이전트에게 보인다(결정 43).

**구현(규칙 파일·프리셋 단계).**

- 위 61줄을 `shared/rules/{test,code,review,done}.md`로 옮겼다(테스트 21·코드 25·리뷰 10·완료 보고 5). 원본은 영역 주인이다 — test·done은 gimi-test, code·review는 gimi-review(사용자 결정). 다른 스킬에는 첫 줄에 `<!-- @shared {파일} origin: {스킬} -->`를 단 바이트가 같은 복사본을 둔다. 프리셋은 `shared/domains/{commerce,kr-commerce-law}/rules.md`이고 원본은 gimi-review다.
- `check.mjs`가 잡는 줄의 `확인`에는 실제 탐지 조건과 오탐 보정에서 뺀 경우를 적었다. 구조 검사가 규칙 파일의 "검사 error·warn" 줄과 `check.mjs`가 내는 지적(`RULE_SEVERITY`)의 ID·등급을 대조한다. 한쪽에만 있거나 등급이 다르면 실패한다.
- 구조 검사는 형식도 본다 — 필수 항목, ID 겹침, 영역·머리, 대상·검사 값, 프리셋 근거의 URL·"출처 없음", 남은 "URL 확인 필요". 이 검사가 초안의 빈 곳 5건(근거 URL 3·경계값 2)을 찾았다.
- `scripts/rules.mjs`(두 스킬에 같은 복사본)가 설정의 `stacks`·`presets`와 회사 규칙의 "끈 프리셋 규칙"(이유가 있는 줄만)을 반영해 규칙을 한 줄씩 보인다. 전문은 `--id`, 테스트에 넣을 경계값은 `--boundaries`(stacks에 맞는 층만)다. 사용자 결정 — 이번 단계에 함께 넣었다. `kr-commerce-law`를 골랐는데 해석 값(`kcl`)이 없으면 해석이 든 규칙(KCL-001·003·004)을 확인 질문으로 올리라고 알린다.
- SKILL.md 표(결정 34)는 측정 뒤에 만든다. 그 전에는 SKILL.md가 `rules.mjs`로 목록을 보고 필요한 규칙만 읽게 한다.
