# gimi 설계

> 기미(氣味)상궁이 임금의 수라를 먼저 맛보듯, 코드를 올리기 전에 먼저 맛본다. 같은 소리의 기미(幾微)는 낌새라는 뜻이다. 문제의 기미를 diff 밖에서도 잡는다.

이 문서가 gimi 설계의 단일 출처다. 결정이 바뀌면 이 문서를 먼저 고친다.

## 1. 무엇을 해결하는가

AI 에이전트가 쓴 코드와 테스트에는 티가 난다. mock이 돌려준 값을 그대로 단언하는 테스트, 실패하자 기대값을 실제값으로 고친 테스트, `catch {}`로 삼킨 에러, `as any`, 실행하지 않고 "통과했어요"라고 하는 보고가 그렇다.

AI 리뷰에도 티가 난다. 지금의 리뷰 스킬은 그 커밋의 diff 안에서만 판단한다. 바뀐 함수를 쓰는 다른 화면, 티켓에 적힌 요구사항, 그 줄을 예전에 일부러 그렇게 둔 이유는 보지 않는다. 사람이 리뷰하며 잡는 결함은 대개 diff 밖에 있다.

gimi는 이 두 가지를 없앤다.

## 2. suta에서 가져오는 것

suta(UI의 AI 슬롭을 없애는 스킬, `Guksu/suta`)가 효과를 낸 장치를 그대로 쓴다.

| suta의 장치 | gimi에서 |
|---|---|
| "AI가 흔히 하는 것 / 대신 / 근거" 금지선 표 | 코드·테스트·리뷰 슬롭 금지선 |
| 정적 검사(`audit.mjs`) — `file:line` + 이유 + 고치는 법, 확실한 것만 error, 예외는 이유 주석 | 테스트·코드 슬롭 검사(`check.mjs`) |
| 하위 문서는 `PATTERN.md` — 스킬 목록에 따로 뜨지 않게 | 테스트 패턴, 분야 프리셋 |
| `@shared-core` 복사본 + 바이트 비교 | 두 스킬이 함께 읽는 규칙 |
| 선택 평가(트리거·패턴) — 문서보다 먼저 쓴다 | 두 스킬의 트리거 평가. decoy에 내장 `/code-review` 설명 포함 |
| 구조 검사(`validateSkills.mjs`) | 같은 방식 |
| 벤치마크 — 같은 요청을 있이·없이, 첫 실행으로 비교, 진 결과도 기록 | 리뷰 품질 측정(방법은 열린 질문) |
| 실사용 점검 루프 — 실제 프로젝트에 써 보고 규칙을 더한다 | 리뷰 지적 → 규칙 후보 → 사람 승인 → 규칙 |
| 한계 절 — "검사가 깨끗해도 끝난 것이 아니다" | 같은 방식 |

## 4. 규칙은 세 겹이다

| 겹 | 내용 | 어디에 | 공개 |
|---|---|---|---|
| 공통 금지선 | 스택별 코드·테스트·리뷰 슬롭 | 스킬 안 | 공개 |
| 분야 프리셋 | 분야의 일반 지식(예: 커머스 — 금액은 정수 원 단위, 주문 상태 전이는 한 곳에서) | 스킬 안 | 공개 |
| 회사 규칙 | 그 회사만의 규칙 | 회사 저장소 안 파일 | 비공개 |

아래 겹이 위 겹을 덮어쓴다. 회사 규칙에서 프리셋의 한 줄을 끌 수도 있다(이유를 적는다).

## 5. 흐름 (초안)

### 처음 설정 — `gimi-review`

1. 분야 프리셋을 고른다(여러 개 가능).
2. 요구사항 출처를 고른다.
3. 코드에서 도메인 규칙 초안을 뽑는다 — enum·union 타입, 상태 전이 함수, 검증 스키마, 금액·날짜 계산 유틸. 줄마다 "확인 필요"를 붙인다.
4. 사람이 확인한 줄만 회사 규칙 파일에 넣는다.
5. 끝내기 전 검사를 이 프로젝트에 켤지 묻는다(결정 9).

### 리뷰 — `gimi-review`

1. 맥락을 모은다 — 스크립트가 맥락 묶음을 만들고, 에이전트가 그것을 읽어 판단한다(아래 "맥락 수집").
2. 금지선·분야 프리셋·회사 규칙과 대조한다.
3. 근거가 있는 지적만 보고한다(결정 12·13). 채팅에는 지적 수와 "고쳐야 함"만 짧게, 전체는 리뷰 기록 파일에 쓴다(결정 14).
4. 같은 종류의 지적이 반복되면 규칙 후보로 올린다. 사람이 승인해야 규칙이 된다.

지적 하나의 형식:

```text
[고쳐야 함] 영향 범위
주문 상태 형태가 바뀌었는데 배지는 예전 형태를 읽는다

바뀐 곳  src/api/order.ts:42
         status: string → { code, label }
근거    src/components/OrderBadge.tsx:12
         status === 'PAID'  (이 PR에서 안 바뀜)
상황    결제 완료 주문 → 배지가 항상 '알 수 없음'
테스트  OrderBadge 테스트 없음
```

- 머리: 단계(고쳐야 함·고치면 좋음·확인 질문) + 맥락 종류(영향 범위·의도·이력·슬롭·도메인 규칙)
- `근거`는 diff 밖이어야 한다. 슬롭 지적만 예외로 diff 안의 줄을 근거로 쓴다.
- `확인 질문`은 상황 대신 "무엇이 어긋나 보이는가 + 의도했다면 무엇을 알려 달라"를 쓴다.

### 맥락 수집 — 스크립트가 모으고 에이전트가 판단한다 (결정 19~23)

| 맥락 | 스크립트(`context.mjs`)가 매번 모으는 것 | 에이전트가 판단하는 것 |
|---|---|---|
| 공통 | 리뷰 범위(PR 번호, 또는 현재 브랜치와 기본 브랜치의 갈림점), 바뀐 파일·줄 | 어느 범위를 볼지 사용자와 확인 |
| 영향 범위 | 바뀐 export와 그 종류(추가·삭제·시그니처 변경·본문만 변경), 사용처 `file:line` + 앞뒤 2줄, 그 사용처가 이 PR에서 함께 바뀌었는지. 지우거나 바꾼 문자열(쿼리 키·라우트 경로·i18n 키·저장소 키)이 쓰이는 다른 곳 | 사용처가 의미상 깨지는지. 필요하면 2단계 이상 따라간다 |
| 의도·요구사항 | PR 제목·본문, 커밋 메시지, 브랜치 이름, 티켓 번호·링크(`SHOP-123` 등), 연결된 GitHub 이슈 본문(`gh pr view --json closingIssuesReferences`) | 외부 출처 본문을 MCP 연결로 읽는다(없으면 붙여 넣기 요청). 요구사항을 항목으로 쪼개 diff와 대조해, 빠진 것과 요청하지 않은 동작 변경을 찾는다 |
| 변경 이력 | 바꾸거나 지운 줄의 blame, 파일마다 최근 커밋 N개(기본 10). 커밋마다 제목·본문·연결 PR. 수정·되돌리기·우회 커밋(fix·revert·hotfix·workaround)을 표시하고, 서식 정리 커밋은 뺀다(`.git-blame-ignore-revs`를 따른다) | 새 변경이 예전 수정을 되돌리거나 건너뛰는지 판단해 "확인 질문"으로 올린다 |
| 출력 | 전체는 JSON 파일, 에이전트에게는 상한이 있는 요약. 못 모은 것은 이유와 함께 "건너뜀" | 건너뛴 맥락이 있으면 보고에 적는다 |

**사용처 찾기(결정 20).** 프로젝트 `node_modules`의 `typescript`를 불러와 언어 서비스의 참조 찾기를 쓴다. 바뀐 export는 바뀐 줄을 감싼 최상위 선언을 옛 파일·새 파일에서 각각 찾아 비교해 종류를 정한다. 본문만 바뀌어도 사용처는 모은다(의미가 바뀌었을 수 있다). 다만 요약에서는 시그니처 변경보다 뒤에 둔다.

**건너뜀의 예.** gh 로그인이 없으면 PR·이슈 본문을 건너뛴다. 얕은 복제(CI의 `fetch-depth: 1`)에서는 이력을 건너뛴다. `typescript`가 없으면 문자열 검색으로 내려간다. 어떤 경우든 "없음"과 "건너뜀"을 구분한다. 사용처를 찾지 못한 것과 찾기를 건너뛴 것은 다르다.

**평가와의 연결.** 결정 15의 채점에서 정답의 근거 위치가 맥락 묶음에 없으면 "수집 실패", 있는데 지적하지 못했으면 "판단 실패"로 나눈다. `context.mjs`는 예제 저장소로 테스트를 먼저 쓴다.

### 테스트 작성 — `gimi-test`

"테스트 써줘" 요청이나 리뷰의 테스트 누락 지적에서 읽힌다. 무엇을 테스트할지(요구사항·도메인 규칙 → 경계값), 어떻게(패턴), 무엇을 하지 않을지(테스트 슬롭 금지선)를 준다.

### 끝내기 전 — `gimi-test`

`check.mjs --changed`가 바뀐 범위의 테스트·타입 검사를 실제로 돌리고, 테스트 슬롭을 검사한다. 보고에는 실행한 명령과 결과를 붙인다. 실행하지 못한 검사는 이유와 함께 "건너뜀"으로 적는다.
