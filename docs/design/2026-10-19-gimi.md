# gimi 설계

> 기미(氣味)상궁이 임금의 수라를 먼저 맛보듯, 코드를 올리기 전에 먼저 맛본다. 같은 소리의 기미(幾微)는 낌새라는 뜻이다. 문제의 기미를 diff 밖에서도 잡는다.

이 문서가 gimi 설계의 단일 출처다. 결정이 바뀌면 이 문서를 먼저 고친다.

## 1. 무엇을 해결하는가

AI 에이전트가 쓴 코드와 테스트에는 티가 난다. mock이 돌려준 값을 그대로 단언하는 테스트, 실패하자 기대값을 실제값으로 고친 테스트, `catch {}`로 삼킨 에러, `as any`, 실행하지 않고 "통과했어요"라고 하는 보고가 그렇다.

AI 리뷰에도 티가 난다. 지금의 리뷰 스킬은 그 커밋의 diff 안에서만 판단한다. 바뀐 함수를 쓰는 다른 화면, 티켓에 적힌 요구사항, 그 줄을 예전에 일부러 그렇게 둔 이유는 보지 않는다. 사람이 리뷰하며 잡는 결함은 대개 diff 밖에 있다.

gimi는 이 두 가지를 없앤다.

## 2. suta에서 가져오는 것

suta(UI의 AI 슬롭을 없애는 스킬, `Guksu/suta`)가 효과를 낸 장치를 그대로 쓴다.

| suta의 장치 | gimi에서 |
|---|---|
| "AI가 흔히 하는 것 / 대신 / 근거" 금지선 표 | 코드·테스트·리뷰 슬롭 금지선 |
| 정적 검사(`audit.mjs`) — `file:line` + 이유 + 고치는 법, 확실한 것만 error, 예외는 이유 주석 | 테스트·코드 슬롭 검사(`check.mjs`) |
| 하위 문서는 `PATTERN.md` — 스킬 목록에 따로 뜨지 않게 | 테스트 패턴, 분야 프리셋 |
| `@shared-core` 복사본 + 바이트 비교 | 두 스킬이 함께 읽는 규칙 |
| 선택 평가(트리거·패턴) — 문서보다 먼저 쓴다 | 두 스킬의 트리거 평가. decoy에 내장 `/code-review` 설명 포함 |
| 구조 검사(`validateSkills.mjs`) | 같은 방식 |
| 벤치마크 — 같은 요청을 있이·없이, 첫 실행으로 비교, 진 결과도 기록 | 리뷰 품질 측정(방법은 열린 질문) |
| 실사용 점검 루프 — 실제 프로젝트에 써 보고 규칙을 더한다 | 리뷰 지적 → 규칙 후보 → 사람 승인 → 규칙 |
| 한계 절 — "검사가 깨끗해도 끝난 것이 아니다" | 같은 방식 |

| 19 | 맥락 수집 분담 | 모으는 건 스크립트(`context.mjs`), 판단은 에이전트 | diff만 보는 것이 AI 리뷰어의 습관이라, 수집을 에이전트 재량에 맡기면 같은 문제가 생긴다. 평가에서 수집 실패와 판단 실패를 나눌 수 있다. 결과가 매번 같아 테스트를 먼저 쓸 수 있다 |

| 25 | 설정 형식 | JSON | 의존성 없이 읽는다. YAML은 파서가 필요하다 |
| 26 | 회사 규칙 형식 | 규칙마다 절 + 고정 항목(왜·대신·확인·검사·근거), 제목에 ID. 규칙 후보는 같은 형식에 상태·출처를 더한다. 프리셋 규칙은 "끈 프리셋 규칙" 절에 이유와 함께 끈다 | 사람이 읽고 PR로 리뷰하기 쉽고, 스크립트도 항목을 읽는다. 표와 달리 긴 글과 정규식의 `\|`에 깨지지 않는다. ID가 있어야 지적·후보·끄기가 규칙을 가리킨다 |
| 27 | 리뷰 기록 | 리뷰마다 Markdown 하나가 정본. 지적마다 `규칙`·`판정` 항목을 둔다. 기록은 커밋하고, 맥락 묶음(`*.context.json`)은 `.gitignore`로 뺀다 | 팀 전체 기록으로 승격을 센다. 판정이 실사용 기록(결정 15②)이 된다. 맥락 묶음은 크고 다시 만들 수 있다. 판정을 JSON에 두면 사람이 고치기 불편하고, 둘 다 두면 어긋난다 |

## 4. 규칙은 세 겹이다

| 겹 | 내용 | 어디에 | 공개 |
|---|---|---|---|
| 공통 금지선 | 스택별 코드·테스트·리뷰 슬롭 | 스킬 안 | 공개 |
| 분야 프리셋 | 분야의 일반 지식(예: 커머스 — 금액은 정수 원 단위, 주문 상태 전이는 한 곳에서) | 스킬 안 | 공개 |
| 회사 규칙 | 그 회사만의 규칙 | 회사 저장소의 `docs/gimi/rules.md` | 비공개 |

아래 겹이 위 겹을 덮어쓴다. 회사 규칙에서 프리셋의 한 줄을 끌 수도 있다(이유를 적는다).

## 5. 흐름 (초안)

### 처음 설정 — `gimi-review`

1. 분야 프리셋을 고른다(여러 개 가능).
2. 요구사항 출처를 고른다.
3. 코드에서 도메인 규칙 초안을 뽑아 `docs/gimi/candidates.md`에 후보로 쓴다 — enum·union 타입, 상태 전이 함수, 검증 스키마, 금액·날짜 계산 유틸. 출처는 `file:line`.
4. 사람이 승인한 후보만 `docs/gimi/rules.md`로 옮긴다.
5. 끝내기 전 검사를 이 프로젝트에 켤지 묻는다(결정 9).
6. 고른 값을 `.agents/gimi.json`에 쓰고, `.gitignore`에 `docs/gimi/reviews/*.context.json`을 더한다(아래 "회사 저장소의 파일").

### 리뷰 — `gimi-review`

1. 맥락을 모은다 — 스크립트가 맥락 묶음을 만들고, 에이전트가 그것을 읽어 판단한다(아래 "맥락 수집").
2. 금지선·분야 프리셋·회사 규칙과 대조한다.
3. 근거가 있는 지적만 보고한다(결정 12·13). 채팅에는 지적 수와 "고쳐야 함"만 짧게, 전체는 리뷰 기록 `docs/gimi/reviews/`에 쓴다(결정 14·27).
4. 규칙에 걸리지 않은 지적이 같은 묶음으로 `promoteAfter`번(기본 3) 쌓이면 `candidates.md`에 후보로 올린다. 판정이 틀림·의도함인 지적은 세지 않는다. 사람이 승인해야 규칙이 된다.

지적 하나의 형식:

```text
[고쳐야 함] 영향 범위
주문 상태 형태가 바뀌었는데 배지는 예전 형태를 읽는다

바뀐 곳  src/api/order.ts:42
         status: string → { code, label }
근거    src/components/OrderBadge.tsx:12
         status === 'PAID'  (이 PR에서 안 바뀜)
상황    결제 완료 주문 → 배지가 항상 '알 수 없음'
테스트  OrderBadge 테스트 없음
```

- 머리: 단계(고쳐야 함·고치면 좋음·확인 질문) + 맥락 종류(영향 범위·의도·이력·슬롭·도메인 규칙)
- `근거`는 diff 밖이어야 한다. 슬롭 지적만 예외로 diff 안의 줄을 근거로 쓴다.
- `확인 질문`은 상황 대신 "무엇이 어긋나 보이는가 + 의도했다면 무엇을 알려 달라"를 쓴다.

### 맥락 수집 — 스크립트가 모으고 에이전트가 판단한다 (결정 19~23)

| 맥락 | 스크립트(`context.mjs`)가 매번 모으는 것 | 에이전트가 판단하는 것 |
|---|---|---|
| 공통 | 리뷰 범위(PR 번호, 또는 현재 브랜치와 기본 브랜치의 갈림점), 바뀐 파일·줄 | 어느 범위를 볼지 사용자와 확인 |
| 영향 범위 | 바뀐 export와 그 종류(추가·삭제·시그니처 변경·본문만 변경), 사용처 `file:line` + 앞뒤 2줄, 그 사용처가 이 PR에서 함께 바뀌었는지. 지우거나 바꾼 문자열(쿼리 키·라우트 경로·i18n 키·저장소 키)이 쓰이는 다른 곳 | 사용처가 의미상 깨지는지. 필요하면 2단계 이상 따라간다 |
| 의도·요구사항 | PR 제목·본문, 커밋 메시지, 브랜치 이름, 티켓 번호·링크(`SHOP-123` 등), 연결된 GitHub 이슈 본문(`gh pr view --json closingIssuesReferences`) | 외부 출처 본문을 MCP 연결로 읽는다(없으면 붙여 넣기 요청). 요구사항을 항목으로 쪼개 diff와 대조해, 빠진 것과 요청하지 않은 동작 변경을 찾는다 |
| 변경 이력 | 바꾸거나 지운 줄의 blame, 파일마다 최근 커밋 N개(기본 10). 커밋마다 제목·본문·연결 PR. 수정·되돌리기·우회 커밋(fix·revert·hotfix·workaround)을 표시하고, 서식 정리 커밋은 뺀다(`.git-blame-ignore-revs`를 따른다) | 새 변경이 예전 수정을 되돌리거나 건너뛰는지 판단해 "확인 질문"으로 올린다 |
| 출력 | 전체는 JSON 파일, 에이전트에게는 상한이 있는 요약. 못 모은 것은 이유와 함께 "건너뜀" | 건너뛴 맥락이 있으면 보고에 적는다 |

**사용처 찾기(결정 20).** 프로젝트 `node_modules`의 `typescript`를 불러와 언어 서비스의 참조 찾기를 쓴다. 바뀐 export는 바뀐 줄을 감싼 최상위 선언을 옛 파일·새 파일에서 각각 찾아 비교해 종류를 정한다. 본문만 바뀌어도 사용처는 모은다(의미가 바뀌었을 수 있다). 다만 요약에서는 시그니처 변경보다 뒤에 둔다.

**건너뜀의 예.** gh 로그인이 없으면 PR·이슈 본문을 건너뛴다. 얕은 복제(CI의 `fetch-depth: 1`)에서는 이력을 건너뛴다. `typescript`가 없으면 문자열 검색으로 내려간다. 어떤 경우든 "없음"과 "건너뜀"을 구분한다. 사용처를 찾지 못한 것과 찾기를 건너뛴 것은 다르다.

**요약 예.**

```text
영향 범위  바뀐 export 3개
  useOrder (반환 형태 변경)  사용처 4
    OrderBadge.tsx:12  이 PR에서 안 바뀜
    OrderList.tsx:30   이 PR에서 바뀜
    …
의도  PR #42 본문, 이슈 #38, SHOP-123(Jira — 에이전트가 읽음)
이력  지운 줄 6 → 커밋 2, 파일 최근 커밋 10
  a3f9c1e fix: iOS 키보드 닫힌 뒤 스크롤 복원 [수정]
건너뜀  없음

전체: docs/gimi/reviews/2026-10-19-pr-42.context.json
```

**평가와의 연결.** 결정 15의 채점에서 정답의 근거 위치가 맥락 묶음에 없으면 "수집 실패", 있는데 지적하지 못했으면 "판단 실패"로 나눈다. `context.mjs`는 예제 저장소로 테스트를 먼저 쓴다.

### 테스트 작성 — `gimi-test`

"테스트 써줘" 요청이나 리뷰의 테스트 누락 지적에서 읽힌다. 무엇을 테스트할지(요구사항·도메인 규칙 → 경계값), 어떻게(패턴), 무엇을 하지 않을지(테스트 슬롭 금지선)를 준다.

### 끝내기 전 — `gimi-test`

`check.mjs --changed`가 바뀐 범위의 테스트·타입 검사를 실제로 돌리고, 테스트 슬롭을 검사한다. 보고에는 실행한 명령과 결과를 붙인다. 실행하지 못한 검사는 이유와 함께 "건너뜀"으로 적는다.

## 6. 회사 저장소의 파일 (결정 24~27)

```text
.agents/
  gimi.json                         설정
docs/gimi/
  rules.md                          회사 규칙 — 정본
  candidates.md                     규칙 후보 — 승인 대기·거절
  reviews/
    2026-10-19-pr-42.md             리뷰 기록 — 커밋한다
    2026-10-19-pr-42.context.json   맥락 묶음 — .gitignore
```

세 Markdown 파일은 같은 방식으로 쓴다. 항목 하나가 `##` 절 하나이고, 절 안에 정해진 항목을 `- 이름: 값`으로 적는다. 사람은 그대로 읽고, 스크립트는 절과 항목을 읽는다.

### 설정 — `.agents/gimi.json`

```json
{
  "stack": "frontend-ts",
  "presets": ["commerce"],
  "requirements": [{ "source": "github" }, { "source": "jira", "keyPattern": "SHOP-\\d+" }],
  "rulePrefix": "SHOP",
  "history": { "recentCommits": 10 },
  "promoteAfter": 3,
  "finishCheck": { "enabled": true }
}
```

| 항목 | 뜻 | 기본값 |
|---|---|---|
| `stack` | 슬롭 규칙·테스트 패턴 묶음 | `"frontend-ts"` |
| `presets` | 분야 프리셋(여러 개) | `[]` |
| `requirements` | 요구사항 출처와 티켓 번호 형식(결정 10·21) | `[{ "source": "github" }]` |
| `rulePrefix` | 회사 규칙 ID의 머리 | `"TEAM"` |
| `history.recentCommits` | 파일마다 볼 최근 커밋 수(결정 22) | `10` |
| `promoteAfter` | 같은 묶음의 지적이 몇 번 쌓이면 후보로 올릴지 | `3` |
| `finishCheck.enabled` | 이 프로젝트에서 끝내기 전 검사를 켤지(결정 9) | `false` |

검증 명령은 `check.mjs`가 `package.json`의 scripts에서 찾는다. 찾지 못하거나 다르게 돌려야 하면 `finishCheck.commands`에 적는다.

### 회사 규칙 — `docs/gimi/rules.md`

```markdown
## SHOP-001 금액은 정수 원 단위로만 계산한다
- 왜: 부동소수 오차로 결제액이 1원 어긋났다(#412)
- 대신: toWon()으로 정수화한 뒤 계산한다
- 확인: 영향 범위 — price·amount의 곱셈·나눗셈
- 검사: /(price|amount)\s*\*\s*0\.\d+/
- 근거: 리뷰 3건에서 승격, 2026-10-12 승인

## 끈 프리셋 규칙
- COM-004 — 쿠폰 중복은 서버에서만 막는다
```

- 제목은 `## {ID} {한 줄 규칙}`이다. ID는 `{rulePrefix}-{세 자리}`이고, 규칙을 지워도 번호를 다시 쓰지 않는다. 옛 리뷰 기록이 그 번호를 가리키기 때문이다.
- `왜`·`대신`·`확인`은 필수다. `검사`(정규식 — 스크립트가 바뀐 줄에서 찾는다)와 `근거`는 선택이다.
- 프리셋 규칙은 "끈 프리셋 규칙" 절에 ID와 이유를 적어 끈다. 이유가 없는 줄은 무시하고 경고한다.
- 프리셋 ID는 분야 머리를 쓴다(커머스 `COM-`). 공통 금지선의 ID 체계는 금지선을 쓸 때 정한다.

### 규칙 후보 — `docs/gimi/candidates.md`

```markdown
## SHOP-007 주문 상태는 orderMachine.ts에서만 바꾼다
- 상태: 대기
- 출처: 리뷰 3건 — reviews/2026-10-02-pr-31.md#2, reviews/2026-10-09-pr-35.md#1, reviews/2026-10-15-pr-40.md#3
- 왜: 화면마다 상태 전이를 따로 하면 결제 취소 후에도 배송 준비로 넘어간다
- 대신: orderMachine.transition()을 부른다
- 확인: 영향 범위 — setStatus·status 대입
```

- 회사 규칙과 같은 형식에 `상태`(대기·거절)와 `출처`를 더한다. 출처는 코드 추출이면 `file:line`, 승격이면 리뷰 기록의 지적 링크다.
- 사람이 채팅에서 승인하면 에이전트가 `rules.md`로 옮긴다. 출처는 `근거` 항목에 남기고 후보에서는 지운다.
- 거절하면 `상태: 거절 — {이유}`로 남긴다. 같은 묶음은 다시 후보로 올리지 않는다.

### 리뷰 기록 — `docs/gimi/reviews/{날짜}-pr-{번호}.md`

PR이 없으면 `{날짜}-{브랜치}.md`로 쓴다.

```markdown
# 리뷰 — PR #42 주문 상태 표시 개선

- 날짜: 2026-10-19
- 범위: main...feat/order-status (커밋 3, 파일 7)
- 맥락: 영향 범위 export 3·사용처 9 / 의도 PR #42·이슈 #38·SHOP-123 / 이력 커밋 12 / 건너뜀 없음
- 결과: 고쳐야 함 1 · 고치면 좋음 2 · 확인 질문 1

## 1. [고쳐야 함] 영향 범위 — 주문 상태 형태가 바뀌었는데 배지는 예전 형태를 읽는다
- 바뀐 곳: `src/api/order.ts:42` — status: string → { code, label }
- 근거: `src/components/OrderBadge.tsx:12` — status === 'PAID' (이 PR에서 안 바뀜)
- 상황: 결제 완료 주문 → 배지가 항상 '알 수 없음'
- 테스트: OrderBadge 테스트 없음
- 규칙: 없음 — 묶음 `api-shape-consumer`
- 판정: 미정
```

- 지적의 항목은 결정 12의 형식과 같다. 채팅에서는 줄 맞춘 글로, 기록에서는 `- 이름: 값`으로 쓴다.
- `규칙`은 걸린 규칙의 ID(공통 금지선·`COM-`·회사 규칙)를 적는다. 걸린 규칙이 없으면 `없음 — 묶음 {짧은 이름}`을 적는다. 승격 집계는 규칙이 없는 지적을 묶음 이름으로 센다.
- `판정`은 미정·맞음·틀림·의도함 중 하나다. 사용자가 채팅으로 알려 주면 에이전트가 고치고, 사람이 파일을 직접 고쳐도 된다. 실사용 기록(결정 15②)의 찾은 비율과 오탐 비율은 이 항목으로 센다.
