사용자가 준 요청은 이렇습니다.

> 기미를 외부 개발자가 이해하고 자신의 PR에 적용할 수 있도록 개선해줘. (…) 기능과 규칙을 더 늘리기보다, 리뷰 판단 기준·평가 신뢰도·첫 사용 경험을 먼저 보완해줘.

이 문서는 요청 끝에 남겨 달라고 한 여섯 가지를 정리합니다. 진행 방식은 사용자가 고른 대로입니다 — "한 PR, 항목마다 커밋 (추천)", "번역 예시만 (추천)", "새 사례에만 가짜 PR (추천)". 새 유료 모델 실행은 하지 않았습니다.

### 고치지 않은 것

- **Vue·Svelte 파일 안의 사용처** — 프로젝트에 typescript가 있으면 찾지 않습니다(#62에서 문서만 지금 동작에 맞췄습니다). 코드 수정은 범위 밖이라 별도 작업으로 남겼습니다.
- **영어 출력** — 리뷰와 기록은 한국어 그대로입니다. 영어 README와 사례 문서에는 번역 예시만 더했습니다(사용자가 고른 것).
- **설계 문서 1절의 문제 정의** — "지금의 리뷰 스킬은 그 커밋의 diff 안에서만 판단한다"는 처음 짚은 문제를 적은 문장이라 지우지 않았습니다. 대신 "2026-10-19에 적은 문제 가설이고, 다른 리뷰 도구를 재서 확인한 것이 아니다"라고 표시했습니다.

### 재지 않은 가설

- 옛 근거 규칙("diff 밖이어야 한다") 때문에 diff 안 버그를 실제로 놓쳤는가 — 재지 않았습니다. 2026-10-31 평가의 결함 32개는 모두 어긴 규칙(프리셋·2차 패턴)이 있는 결함입니다. 그래서 규칙 없이 바뀐 줄만으로 설명되는 결함은 그 평가에 없었습니다. 그 평가에서 gimi가 놓친 정답 1개(`COM-026`)는 내용은 맞고 위치가 4줄 어긋난 것입니다.
- 결정 64가 diff 안 지적을 늘려 소음이 늘어나는가 — 재지 않았습니다.
- 모델이 `생긴 때`(이번 변경·변경 전부터)를 정확히 가르는가 — 재지 않았습니다.
- 정답 밖 지적 수(gimi 19, `/code-review` 55)의 차이가 오탐의 차이인가 — 내용을 판정하지 않았으므로 말할 수 없습니다.

## 2. 바꾼 판단 기준과 설계 이유

**설계 결정 64 — 근거 위치와 실패 조건**

- diff 밖 맥락(영향 범위·의도·이력·CI)은 지적이 있든 없든 확인합니다.
- 결함의 근거는 diff 안팎 어디든 됩니다. 바뀐 함수 안의 계산·분기만으로 실패가 설명되면 그 줄이 근거입니다. 맥락 종류는 "바뀐 코드"입니다.
- 모든 지적의 `상황`에는 어떤 입력·상태에서 무엇이 잘못되는지를 씁니다. 쓸 수 없으면 추측이나 취향이라 보고하지 않습니다.
- `생긴 때`는 이번 변경인지, 변경 전부터인지를 적습니다. 변경 전부터 있던 결함은 "고쳐야 함"으로 올리지 않습니다. 이 PR을 막을 이유가 아니기 때문입니다. 이 부분과 항목 이름은 제가 정했습니다.
- 사용처를 찾았는데 없는 것과, 건너뛰었거나 검색하지 못한 것을 나눕니다. 건너뛴 맥락에 기댄 결론은 단정하지 않습니다.
- 이유: 요청의 기준을 그대로 옮겼습니다 — "결함의 근거는 diff 안팎 어디에 있어도 인정한다", "기존 결함과 이번 변경이 만든 결함을 구분한다".
- `review/diff-only`의 ID는 측정 기록(`evals/slop/README.md`) 때문에 그대로 두었습니다. 확인 문구만 바꿨고, 옛 측정은 옛 기준이라고 적었습니다.

**설계 결정 65 — 평가의 판정과 조건**

- 위치 점수는 그대로 두고, 사람이 내용을 읽고 판정한 것을 따로 셉니다. `score`가 `judgments.json`을 만들고 모든 항목을 미검토로 둡니다.

  | 항목 | 판정 값 |
  |---|---|
  | 위치로 찾은 정답 | 원인·실패 조건 일치 · 불일치 |
  | 위치로 놓친 정답 | 다른 위치에서 찾음 · 못 찾음 |
  | 정답 밖 지적·결함 없는 PR의 지적 | 실제 결함 · 잘못된 지적 · 판단 보류 |

- 다시 채점해도 사람이 적은 판정은 지킵니다.
- 실행마다 모델·gimi 판(버전·커밋·커밋하지 않은 수정)·도구·반복 횟수와 그때의 정답·diff 조각을 남깁니다.
- 결함 정의에 `github` 필드를 더했습니다. 가짜 PR #7·체크·실패 로그를 줄 수도 있고, gh를 쓸 수 없는 상태를 만들 수도 있습니다. 이 필드가 없는 기존 결함은 지난 평가와 같은 조건입니다.
- 이유: 요청한 기준 — "위치 일치 점수는 유지하더라도 의미상 탐지와 구분", "사람이 확인하지 않은 결과는 미검토 상태로 유지", "과거 평가 결과는 소급해서 바꾸지 마".

- **`score`가 사람이 적은 판정을 조용히 지울 수 있었다.** 모양이 다른 판정 파일을 덮어쓰거나, 짝 없는 판정을 버리는 경우입니다. 지금은 실패하거나 `orphans`로 남깁니다.
- **`/code-review`가 사례 2를 놓친 것처럼 읽혔다.** 실제로는 위치로는 찾았고, 요구사항을 짚은 것이 2번 중 1번입니다.
- **가짜 gh가 `gh pr checkout 7`에 "PR 없음"으로 답했다.** SKILL.md는 PR이면 이 명령부터 돌립니다.
- **지침의 "상황을 쓸 수 없으면 보고하지 않는다"가 확인 질문과 부딪쳤다.** 확인 질문은 예외라고 SKILL.md와 결정 64에 적었습니다.
