# race-and-duplicate — 다시 그려도, 다시 열어도, 겹쳐 와도 한 번

## 언제 쓰는가

결제하기 버튼, 결제 결과 화면, 검색·금액 다시 계산처럼 **요청이나 이벤트를 보내는 화면**을 쓰거나 바꿀 때 쓴다. 화면은 생각보다 자주 다시 그려지고 다시 열린다. 손님은 버튼을 두 번 누르고, 결과 화면을 새로 고치고, 뒤로 갔다 다시 온다. 개발 모드의 StrictMode는 effect를 일부러 두 번 돌린다. 느린 응답은 나중 요청보다 늦게 온다.

관련 규칙은 `COM-028`(구매 이벤트는 주문마다 고유한 거래 ID로 한 번만)과 `COM-016`(결제 요청은 한 번)이다. 서버 쪽의 같은 문제는 [`idempotency`](../idempotency/PATTERN.md)가 다룬다.

## 무엇을 단언하는가

| 일부러 만드는 것 | 단언 |
|---|---|
| 버튼 연타(응답을 기다리는 동안) | 보낸 요청 수가 1 |
| 결과 화면 새로 고침·다시 열기 | 나간 구매 이벤트 수가 주문마다 1, 거래 ID는 주문번호 |
| StrictMode(effect 두 번) | 확정 요청 수가 1 |
| 늦게 온 예전 응답 | 화면은 최신 응답의 결과, 예전 결과로 바뀌지 않는다 |

세는 대상은 화면 밖으로 나간 것이다. 요청은 MSW 핸들러에서, 이벤트는 `window`에서 듣고 센다.

## 예시

| 파일 | 무엇을 |
|---|---|
| `assets/purchase-once.test.tsx` | 좋은 예시 — 결과 화면 새로 고침, 다른 주문, StrictMode, 결제하기 연타, 늦게 온 금액 응답 |
| `assets/purchase-once.slop.test.tsx` | 슬롭 예시 — 결과 화면을 한 번만 열고 구매 이벤트가 나갔는지만 본다 |

새로 고침은 화면을 내렸다가 같은 주소로 다시 여는 것으로 만든다. 브라우저 저장소는 남는다.

```tsx
const first = openAt(returnUrl(7))
await screen.findByRole('heading', DONE)

first.unmount()
openAt(returnUrl(7))
await screen.findByRole('heading', DONE)

expect(purchases).toEqual([{ transactionId: '7', value: 15000, currency: 'KRW' }])
```

늦게 온 응답은 핸들러가 예전 요청의 응답을 붙잡아 두었다가 최신 응답 뒤에 놓아주는 것으로 만든다. 시간을 기다리지 않는다.

보낸 구매 이벤트를 기록하지 않게 바꾸면 좋은 예시는 새로 고침 경우에서 이벤트가 두 번 나가 실패하고, 슬롭 예시는 그대로 통과한다.

## AI가 흔히 쓰는 테스트 / 대신

| 흔히 | 왜 놓치나 | 대신 |
|---|---|---|
| 화면을 한 번 열고 이벤트가 나갔는지만(`toHaveBeenCalled`) | 두 번 나가도 통과한다 | 다시 열고, 나간 횟수와 내용을 센다 |
| 클릭 한 번 | 연타를 시험하지 않는다 | 응답을 붙잡아 두고 `dblClick` + 한 번 더 |
| 응답을 바로 돌려준다 | 기다리는 동안의 연타가 시험되지 않는다 | 핸들러가 약속을 기다리게 한다 |
| 응답 순서가 늘 요청 순서 | 늦게 온 예전 응답이 덮어쓰는 결함을 놓친다 | 예전 응답을 최신 응답 뒤에 놓아준다 |
| StrictMode 없이 렌더링 | 개발 모드에서만 두 번 도는 effect를 놓친다 | `<StrictMode>`로 감싸 한 번 더 |

## 주의사항

- 새로 고침을 흉내 낼 때 브라우저 저장소를 지우지 않는다. 실제 새로 고침에서도 남는다. 테스트끼리는 `afterEach`에서 지운다.
- 이벤트 리스너는 테스트가 끝나면 뗀다. 다음 테스트의 이벤트를 세게 된다.
- "늦은 응답이 화면까지 갈 차례"를 줄 때는 응답이 나간 것을 확인한 뒤 대기열을 한 번 비운다(`setTimeout(…, 0)`). 시간을 늘려 기다리지 않는다.
