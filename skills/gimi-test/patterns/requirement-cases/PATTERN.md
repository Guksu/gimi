# requirement-cases — 요구사항 한 항목에 테스트 하나

## 언제 쓰는가

티켓·PR 본문·기획 문서에 요구사항이 적힌 기능을 테스트할 때 쓴다. 구현을 보고 테스트를 쓰면 테스트는 구현과 같은 실수를 한다. 기준 금액을 쿠폰 전 금액으로 잘못 잡은 구현에서, 구현을 보고 쓴 테스트도 쿠폰 전 금액을 넣는다. 요구사항을 보고 쓰면 테스트가 구현과 다른 곳에서 출발해 어긋남이 드러난다.

관련 규칙은 `COM-029`(무료 배송 기준의 경계는 요구사항 문구대로)다. 리뷰에서는 같은 일을 "의도" 맥락이 한다. PR 본문의 요구사항을 항목으로 쪼개 diff와 맞춰 본다.

## 무엇을 단언하는가

| 단언 | 왜 |
|---|---|
| 요구사항 항목마다 테스트 하나, 이름은 그 문장 | 테스트 목록이 곧 요구사항 점검표가 된다. 빠진 항목이 보인다 |
| 항목의 경계(기준 바로 아래·정확히 기준) | "이상"·"초과", "할인 전"·"할인 뒤"가 갈리는 곳이다 |
| 항목끼리 겹치는 경우(쿠폰 + 포인트) | 항목마다는 맞아도 함께 쓰면 틀리는 결함을 잡는다 |
| 문서에 없는 경우는 `it.todo` | 정하지 않은 것을 테스트로 굳히지 않고 묻는다 |

## 예시

| 파일 | 무엇을 |
|---|---|
| `assets/shipping-requirements.test.ts` | 좋은 예시 — 배송비 정책 세 항목과 첫 항목의 경계, 문서에 없는 경우의 `it.todo` |
| `assets/shipping-requirements.slop.test.ts` | 슬롭 예시 — 구현의 이름(`subtotal`·`FREE_SHIPPING_THRESHOLD`)을 따라 쓰고 쿠폰을 쓰는 경우가 없다 |

요구사항 문장을 그대로 테스트 이름으로 옮긴다.

```ts
describe("요구사항 — 배송비 정책", () => {
  it('1. 쿠폰을 적용한 뒤 상품 금액이 30,000원 이상이면 배송비 0원', …)
  it('1의 경계 — 쿠폰을 적용해 30,000원 아래로 내려가면 배송비가 붙는다(32,000원 − 3,000원)', …)
  it('2. 그 밖에는 배송비 3,000원', …)
  it('3. 포인트는 배송비를 정할 때 빼지 않는다', …)
  it.todo('문서에 없음 — 제주·도서 산간의 추가 배송비. 기획에 묻고 정한다')
})
```

배송비를 쿠폰 전 상품 금액으로 정하게 바꾸면(요구사항은 쿠폰 뒤), 좋은 예시는 "1의 경계"에서 실패하고 슬롭 예시는 그대로 통과한다.

## AI가 흔히 쓰는 테스트 / 대신

| 흔히 | 왜 놓치나 | 대신 |
|---|---|---|
| 구현의 분기마다 테스트 | 구현에 없는 요구사항은 시험되지 않는다 | 요구사항 항목마다 |
| 테스트 이름이 함수·변수 이름 | 무엇을 지키는 테스트인지 요구사항과 맞춰 볼 수 없다 | 요구사항 문장 |
| 항목마다 정상값 하나 | "할인 뒤"·"이상" 같은 문구가 갈리는 곳을 지나친다 | 항목의 경계도 함께([`domain-boundaries`](../domain-boundaries/PATTERN.md)) |
| 문서에 없는 경우를 짐작해 단언 | 정하지 않은 것을 테스트가 굳힌다 | `it.todo`로 남기고 묻는다 |
| 요구사항을 읽지 않고 "테스트 추가" | 무엇이 빠졌는지 모른다 | 요구사항을 먼저 항목으로 쪼갠다 |

## 주의사항

- 요구사항의 출처(티켓 번호·문서 이름)를 `describe` 이름이나 주석에 단다. 요구사항이 바뀌면 고칠 곳을 찾는다.
- 요구사항이 모호하면(무엇이 "상품 금액"인가) 테스트를 쓰기 전에 묻는다. 짐작으로 쓴 테스트는 짐작을 굳힌다.
- 백엔드는 API로, 프론트는 화면의 문구·버튼으로 단언한다. 요구사항이 손님에게 보이는 결과로 적혀 있기 때문이다.
