# external-api-fake — 외부 API는 HTTP 가짜 서버로 바꾼다

## 언제 쓰는가

PG 승인·조회·취소, 배송 접수, 알림 발송처럼 **우리 서버가 외부 API를 부르는 코드**를 쓰거나 바꿀 때 쓴다. 외부 API의 결함은 대개 실패 쪽에 있다. 4xx(확실한 거절)와 5xx·타임아웃(결과를 모름)을 구분하지 못하면, 승인된 결제를 실패로 처리해 손님이 두 번 결제한다.

HTTP 가짜 서버(fake)는 외부 API와 같은 주소 모양·같은 응답을 돌려주는 테스트용 서버다. 우리 코드의 HTTP 클라이언트·타임아웃·오류 변환은 실물로 돈다.

관련 규칙은 `COM-019`(승인 결과가 불확실하면 실패로 단정하지 않는다)다. 경계값은 `node <이 스킬 폴더>/scripts/rules.mjs --id COM-019`에서 가져온다.

## 무엇을 단언하는가

| 가짜 서버의 동작 | 단언 |
|---|---|
| 승인(200) | 결제 완료, 외부에도 승인으로 남는다 |
| 거절(4xx) | 결제 실패, 다시 결제할 수 있다 |
| 오류(5xx) | 실패로 단정하지 않는다 — 결제 대기 그대로, 다시 시도할 수 있다 |
| 늦은 응답(타임아웃) — 외부는 이미 승인 | 다시 조회해 결과를 정한다. 결제 완료 |
| 조회도 실패 | "확인 중"으로 답하고 나중에 맞춘다(웹훅·대사) |

## 예시

| 파일 | 무엇을 |
|---|---|
| `assets/pg-confirm.test.ts` | 좋은 예시 — 가짜 PG의 승인·거절·오류·늦은 응답마다 주문 상태와 다시 결제할 수 있는지 |
| `assets/pg-confirm.slop.test.ts` | 슬롭 예시 — PG 연동 모듈을 `vi.mock`하고 늘 승인을 돌려준다. 타임아웃을 실패로 처리해도 통과한다 |

예시의 `t.pg`는 테스트 안에서 띄운 가짜 PG다. `behavior`로 다음 승인 요청의 결과를 정한다.

```ts
// 시간 제한을 짧게 다시 띄우고, 가짜 PG는 승인한 뒤 그보다 늦게 답한다
await t.close()
t = await startApp({ pgTimeoutMs: 300 })
const { order, paymentKey } = await orderWithCheckout(t)
t.pg.behavior.confirm = 'slow'
t.pg.behavior.delayMs = 1000

const res = await confirm(order.id, paymentKey, order.total)

expect([res.status, res.body.status]).toEqual([200, 'paid'])
```

타임아웃은 짧게 주입한다. 실제 기본값(수 초)을 기다리지 않는다. 대신 그 테스트만 짧게 두고, 나머지 테스트는 넉넉한 시간 제한으로 돌린다. 짧은 기본값은 느린 CI에서 첫 요청이 시간을 넘겨 가끔 깨진다.

PG가 시간 안에 답하지 않으면 실패로 처리하게 바꾸면, 좋은 예시는 늦은 응답에서 402가 와서 실패하고 슬롭 예시는 그대로 통과한다.

## AI가 흔히 쓰는 테스트 / 대신

| 흔히 | 왜 놓치나 | 대신 |
|---|---|---|
| HTTP 클라이언트·연동 모듈을 `vi.mock`하고 승인을 돌려준다 | 타임아웃·오류 변환·재시도가 한 줄도 돌지 않는다 | HTTP 가짜 서버 |
| 성공 경로 하나 | 실패 쪽 결함(타임아웃을 실패로)이 시험되지 않는다 | 승인·4xx·5xx·늦은 응답을 한 묶음으로 |
| 5xx와 4xx를 같은 "실패"로 기대 | 결과를 모르는 경우를 확실한 거절로 처리한 결함을 놓친다 | 5xx·타임아웃은 "결제 대기"나 "확인 중" |
| 실제 샌드박스(결제사 테스트 환경)를 부른다 | 느리고, 네트워크에 따라 깨지고, 실패 응답을 마음대로 만들 수 없다 | 가짜 서버 + 샌드박스는 따로 계약 확인 |
| 타임아웃을 실제 기본값만큼 기다린다 | 테스트가 느려지고 시간에 기대 가끔 깨진다 | 시간 제한을 주입해 짧게 |

## Jest와 다른 줄

| Vitest | Jest |
|---|---|
| `vi.mock`·`vi.hoisted`(슬롭 예시) | `jest.mock` — 같은 이유로 쓰지 않는다 |

가짜 서버 쪽은 테스트 도구와 상관없다.

## 주의사항

- 가짜 서버는 실제 API의 이름과 모양을 그대로 베끼지 않아도 된다. 우리 코드가 기대하는 계약(경로·상태 코드·본문)을 지키면 된다. 실제 API와 어긋나지 않는지는 계약 테스트나 샌드박스 확인으로 따로 본다.
- 가짜 서버의 상태(결제 목록)는 테스트마다 새로 만든다.
- 외부에서 보낸 웹훅도 가짜 서버가 보내게 하면 확정 요청과 웹훅이 겹치는 경우를 함께 시험할 수 있다([`idempotency`](../idempotency/PATTERN.md)).
