# transaction-boundary — 실패하면 모두 되돌리고, 외부 호출은 커밋 뒤에

## 언제 쓰는가

주문 생성처럼 **여러 표를 한 번에 바꾸는 작업**을 쓰거나 바꿀 때 쓴다. 재고를 줄이고, 쿠폰 사용 수를 늘리고, 포인트를 깎고, 주문을 저장한다. 이 가운데 하나라도 실패하면 모두 되돌아가야 한다. 한 단계만 트랜잭션 밖(다른 연결, 다른 서비스의 저장소)에서 바뀌면, 실패한 주문의 포인트만 깎인 채 남는다.

외부 호출(PG 승인·취소, 메일)은 되돌릴 수 없다. 그래서 트랜잭션 안에서 부르지 않고, 결과를 받은 뒤에 짧은 트랜잭션으로 저장한다(공통 금지선 `code/call-in-transaction`).

관련 규칙은 `COM-007`(재고·쿠폰·포인트는 확인과 차감을 원자적으로)이다. 경계값은 `node <이 스킬 폴더>/scripts/rules.mjs --id COM-007`에서 가져온다.

## 무엇을 단언하는가

| 단언 | 왜 |
|---|---|
| 실패한 작업 뒤에 그 작업이 건드리는 값(재고·쿠폰 사용 수·사용 기록·포인트·주문 수)이 모두 작업 전과 같다 | 주문이 안 생긴 것만 보면 트랜잭션 밖에서 바뀐 값을 놓친다 |
| 같은 작업이 성공하면 그 값들이 한 번씩 바뀐다 | 세는 값이 실제로 이 작업이 바꾸는 값인지 확인한다(아무것도 안 바뀌는 값을 세면 늘 통과한다) |
| 실패는 마지막 단계에 넣는다 | 앞 단계가 모두 실행된 뒤라야 되돌림을 시험한다 |
| 외부 호출이 실패하면 우리 쪽 기록(결제 기록·적립·상태)이 그대로다 | 외부 결과를 받기 전에 저장하면 실패한 결제가 성공처럼 남는다 |

## 예시

| 파일 | 무엇을 |
|---|---|
| `assets/order-rollback.test.ts` | 좋은 예시 — 주문 상품 저장에 실패를 넣고 재고·쿠폰·포인트를 모두 센다. 같은 주문의 성공도 세고, PG 승인 오류 뒤에 결제 기록·적립이 없는지 본다 |
| `assets/order-rollback.slop.test.ts` | 슬롭 예시 — 실패를 넣고 응답과 주문 수만 본다. 포인트가 깎인 채 남아도 통과한다 |

실패는 DB 트리거로 넣으면 앱 코드를 바꾸지 않고 원하는 단계에서 일으킬 수 있다. 트리거는 표를 비워도 남으니 테스트마다 지운다.

```ts
await t.db.query("CREATE OR REPLACE FUNCTION injected_failure() RETURNS trigger AS $$ BEGIN RAISE EXCEPTION 'injected failure'; END $$ LANGUAGE plpgsql")
await t.db.query('CREATE TRIGGER injected_failure BEFORE INSERT ON order_items FOR EACH ROW EXECUTE FUNCTION injected_failure()')

const before = await touched()
const res = await order('k-fail')

expect(res.status).toBe(500)
expect(await touched()).toEqual(before) // 재고·쿠폰·포인트·주문 수를 한꺼번에
```

포인트 차감을 트랜잭션이 아니라 풀의 다른 연결로 하도록 바꾸면 좋은 예시는 포인트가 4,000으로 남아 실패하고, 슬롭 예시는 그대로 통과한다.

## AI가 흔히 쓰는 테스트 / 대신

| 흔히 | 왜 놓치나 | 대신 |
|---|---|---|
| 성공 경로만 본다 | 되돌림은 실패할 때만 일어난다 | 마지막 단계에 실패를 넣는다 |
| 실패를 넣고 응답 코드·주문 수만 본다 | 주문은 롤백돼도 다른 연결에서 바꾼 값은 남는다 | 작업이 건드리는 값을 모두 센다 |
| 첫 단계에서 실패시킨다(빈 장바구니·잘못된 입력) | 아무것도 바꾸기 전에 끝나 되돌림을 시험하지 않는다 | 앞 단계가 모두 실행된 뒤에 실패시킨다 |
| 저장소·서비스를 mock해 예외를 던진다 | 실제 트랜잭션과 연결이 없어 경계를 시험하지 못한다 | 실제 DB에서 트리거·제약으로 실패를 만든다 |
| 외부 호출 실패를 mock 호출 횟수로 본다 | 우리 쪽에 무엇이 저장됐는지 모른다 | 가짜 서버로 실패시키고 우리 표를 센다 |

## Jest와 다른 줄

다른 줄이 없다. 트리거·supertest는 Jest에서도 같다.

## 주의사항

- 실패를 넣는 트리거·함수 이름은 테스트 전용으로 짓고, `afterEach`에서 지운다. 남으면 다음 테스트 파일이 이유 없이 실패한다.
- DB 제약으로 실패를 만들 수 있으면(유니크·CHECK) 트리거보다 그쪽이 낫다. 실제로 일어나는 실패라서다.
- 동시에 들어와 실패하는 경우(같은 쿠폰을 동시에)는 [`concurrency`](../concurrency/PATTERN.md)로 따로 본다.
- 외부 호출이 실패했을 때 다시 시도할 수 있는지는 [`external-api-fake`](../external-api-fake/PATTERN.md)와 함께 본다.

| Java·Kotlin | 같은 DB 트리거, 또는 `@SpyBean`으로 마지막 저장소만 예외 | JdbcTemplate로 조회 — `@Transactional` 테스트는 롤백을 가려 쓰지 않는다 |

| Go | 같은 DB 트리거 | `database/sql`로 조회 |
