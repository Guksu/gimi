# gimi-test — 티 나지 않는 테스트와 끝내기 전 확인

AI가 쓴 테스트는 통과하지만 아무것도 지키지 않는 경우가 많다. mock이 돌려준 값을 그대로 단언하고, 실패하면 기대값을 실제값으로 고치고, 실행해 보지 않고 "통과했어요"라고 보고한다. 이 스킬은 결함이 있으면 실패하는 테스트를 쓰게 하고, 끝내기 전에 실제로 돌려 확인하게 한다.

## 지금 상태 (0.0.1)

끝내기 전 검사 스크립트(`scripts/check.mjs`)는 바뀐 범위의 테스트·타입 검사·린트를 찾아 돌리고, 바뀐 JS·TS 줄에서 테스트·코드 슬롭을 찾아 보고한다. `--baseline`으로 실패를 기준에서 다시 돌려 보고, `scripts/connect.mjs`로 프로젝트별로 자동 실행을 연결한다. 테스트 금지선(`shared/rules/test.md`·`done.md`)과 분야 프리셋(`shared/domains/`)이 들어 있고, `scripts/rules.mjs`가 설정에 맞는 것만 보인다. 테스트 패턴은 1차 가운데 8개(프론트 `api-boundary`, 백엔드 `concurrency`·`idempotency`·`webhook-contract`·`external-api-fake`, 둘 다 `domain-boundaries`·`requirement-cases`·`regression-first`)가 들어 있다. 나머지는 차례로 더한다. 슬롭 검사는 정규식 수준이라 놓치는 것이 있으니 아래 "쓰지 않을 테스트"도 직접 확인한다.

## 테스트를 쓸 때

1. **무엇을 지킬지부터 정한다.** 티켓·PR의 요구사항을 항목으로 쪼개고, 항목마다 테스트 이름을 하나씩 붙인다. 구현을 따라 테스트를 쓰지 않는다.
2. **경계값을 뽑는다.** `node <이 스킬 폴더>/scripts/rules.mjs --boundaries`로 분야 프리셋·회사 규칙(`docs/gimi/rules.md`)의 경계값 가운데 이 프로젝트의 층(설정 `stacks`)에 맞는 것을 본다. 바꾸는 코드에 닿는 규칙의 경계값을 테스트 입력으로 쓴다. 없으면 0·1·최대·최대 + 1, 빈 값, 같은 요청 두 번을 넣는다.
3. **패턴을 고른다.** 아래 "테스트 패턴" 표에서 상황에 맞는 패턴의 `PATTERN.md`를 읽는다. 무엇을 단언할지와 AI가 흔히 쓰는 테스트가 적혀 있고, `assets/`의 좋은 예시와 슬롭 예시를 나란히 볼 수 있다. 맞는 패턴이 없으면 아래 단계만 따른다.
4. **경계만 가짜로 바꾼다.** 테스트 대상은 실물로 두고, 네트워크(프론트는 MSW, 백엔드는 HTTP 가짜 서버)·시간(가짜 타이머)·외부 결제만 바꾼다. 테스트 대상 모듈이나 저장소(DB)를 통째로 mock하지 않는다.
5. **사용자가 보는 결과를 단언한다.** 프론트는 역할·이름으로 찾고 화면 결과를 본다. 백엔드는 응답·DB 상태·부수효과 횟수를 본다. 내부 state·호출 횟수만 보는 단언은 쓰지 않는다.
6. **버그 수정은 재현 테스트부터 쓴다.** 고치기 전 코드에서 그 테스트가 실패하는지 먼저 확인한다.

## 테스트 패턴

패턴마다 `patterns/{패턴}/PATTERN.md`와 예시(`assets/*.test.ts(x)` 좋은 예시, `assets/*.slop.test.ts(x)` 슬롭 예시)가 있다. 좋은 예시는 결함을 심은 앱에서 실패하고, 슬롭 예시는 같은 결함을 놓치고 통과한다. 예시의 도우미(`startApp`·`openAt`·`server`)는 예시 앱의 것이니 프로젝트의 같은 역할 도우미로 바꿔 쓴다.

## 백엔드에서 더 볼 것

- 동시성 — 재고 1개에 동시 주문 N건이면 성공은 1건이어야 한다. 순차 호출 두 번으로 대신하지 않는다.
- 멱등성 — 같은 멱등 키로 재시도하거나 같은 결제를 두 번 확정해도 부수효과는 한 번이어야 한다.
- 웹훅 — 서명이 틀린 요청, 같은 이벤트 두 번, 역순 도착, 모르는 type을 보낸다.
- 저장소 — 실제 DB로 제약(유니크·외래키)을 확인하고, 테스트마다 데이터를 격리한다.

## 끝내기 전에

1. `node <이 스킬 폴더>/scripts/check.mjs`를 돌린다. 기준 브랜치와의 갈림점부터 지금 작업 트리까지(커밋하지 않은 변경·새 파일 포함)가 범위다. 명령은 설정 `finishCheck.commands`(`.agents/gimi.json`), guksu-harness 검증 설정, 프로젝트 파일(`package.json`·`build.gradle`·`pom.xml`·`pyproject.toml`·`go.mod`) 순서로 찾는다. 무엇을 돌릴지 먼저 보려면 `--dry-run`, 기준이 기본 브랜치가 아니면 `--base 브랜치`를 붙인다.
2. 종료 코드가 1이면 실패한 명령의 출력 끝이나 슬롭 `error` 줄을 보고 고친 뒤 다시 돌린다. 2면 사용법·환경 문제다.
3. 슬롭 줄은 `등급 ID 파일:줄 상황 — 대신`이다. `error`는 확실한 결함(`.only`, 단언 없는 테스트, 대상 모듈 통째 mock, 실패를 삼키는 try/catch·if, 빈 catch, `debugger`)이라 고친다. `warn`은 판단해서 고치거나, 그대로 두면 이유를 보고에 적는다.
4. 일부러 남길 줄은 그 줄 끝이나 바로 윗줄에 `// gimi-ignore: {ID} — {이유}`를 단다. 이유가 없으면 무시하지 않는다. 지적을 피하려고 무시 주석을 달지 않는다.
5. 보고에는 스크립트가 낸 명령·결과·범위(관련 테스트만·전체)·슬롭 줄을 그대로 붙인다. "건너뜀" 줄도 이유와 함께 붙인다. 돌리지 않은 검사를 통과했다고 쓰지 않는다.
6. 실패를 "원래 있던 실패"라고 하려면 `--baseline`을 붙여 다시 돌린다. 실패한 명령을 기준(갈림점)의 코드에서 다시 돌려 "기준에서는 통과"(이 변경에서 생긴 실패)인지 "기준에서도 실패"인지 `기준` 줄로 알려 준다. 그 줄을 보고에 붙인다.
7. 테스트를 통과시키려고 기대값을 고치거나 `skip`을 붙이거나 스냅샷을 갱신했다면 보고에 밝힌다. 스크립트가 `done/test-bent`·`test/rewritten-expectation`으로 알려 준다.

## 끝내기 전 검사를 자동으로 돌게 하기 (프로젝트별 옵트인)

사용자가 이 프로젝트에서 끝내기 전 검사를 늘 돌게 해 달라고 할 때만 연결한다. 프로젝트 파일과 훅 설정을 바꾸므로 먼저 `--dry-run`으로 무엇이 바뀌는지 보여 주고 확인을 받는다.

1. `node <이 스킬 폴더>/scripts/connect.mjs --dry-run`으로 바뀔 파일을 보이고, 확인을 받은 뒤 `--dry-run` 없이 돌린다.
2. 스크립트는 `check.mjs`와 `lib/`를 `.agents/gimi/check/`에 복사하고 `.agents/gimi.json`의 `finishCheck.enabled`를 켠다. guksu-harness verifier가 있으면 그 설정에 gimi 항목을 더하고(하네스가 돌리는 명령은 다시 돌리지 않는다), 없으면 Claude Code·Codex의 Stop 훅에 등록한다. 앱은 `--app claude|codex|both`로 정한다.
3. Stop 훅이 끝내기를 막으면 보고에 나온 실패를 고친 뒤 끝낸다. "보고하고 끝낸다"는 말이 붙으면 더 고치지 말고 남은 실패를 사용자에게 보고한다.
4. 잠시 끄려면 `finishCheck.enabled`를 false로 한다. 연결을 되돌리려면 `connect.mjs --remove`를 돌린다. 손으로 고친 복사본은 덮어쓰거나 지우지 않고 "충돌"로 알린다.

## 쓰지 않을 테스트

- 단언이 없거나 늘 참인 단언(`expect(true).toBe(true)`)
- `.only`·이유 없는 `.skip`이 남은 테스트
- 실제 시간을 기다리거나(`setTimeout`·`sleep`) 고정하지 않은 현재 시각에 기대는 테스트
- `try/catch`로 실패를 삼키거나 `if` 안에 단언을 둔 테스트
- 실제 외부 API(결제 샌드박스 포함)를 부르는 테스트
- 재시도 설정으로 가끔 깨지는 것을 덮은 테스트

전체 목록은 `node <이 스킬 폴더>/scripts/rules.mjs --area test,done`, 한 줄의 왜·대신·확인은 `--id test/mock-echo`처럼 본다. 금지선은 아직 측정 전이라 모두 가설이다.

## 쓰지 않는 경우·한계

- 코드 리뷰와 도메인 규칙 설정은 gimi-review의 몫이다.
- 예시 코드는 프론트·백엔드 모두 TypeScript(Vitest)로 쓴다. 다른 언어는 원칙을 그 언어의 도구로 옮긴다.
