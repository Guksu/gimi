# gimi-review — diff 밖까지 보는 코드 리뷰

AI 리뷰어는 diff 안에서만 판단한다. 바뀐 함수를 쓰는 다른 화면, 티켓에 적힌 요구사항, 그 줄을 예전에 일부러 그렇게 둔 이유는 보지 않는다. 사람이 리뷰하며 잡는 결함은 대개 diff 밖에 있다. 이 스킬은 그 맥락을 먼저 모으고, 근거가 있는 지적만 남긴다.

## 지금 상태 (0.0.1)

맥락 수집 스크립트(`scripts/context.mjs`)는 범위·바뀐 파일·의도·이력·영향 범위를 모으고, 계약 파일(OpenAPI·GraphQL 스키마)이 바뀌면 바뀐 엔드포인트·필드와 그 사용처를 찾는다. proto와 코드 안의 GraphQL typeDefs는 아직 읽지 않는다. 규칙은 공통 금지선(`shared/rules/`), 분야 프리셋(`shared/domains/` — `commerce`·`kr-commerce-law`), 회사 규칙(`docs/gimi/rules.md`) 세 겹이고, `scripts/rules.mjs`가 설정에 맞는 것만 보인다. 공통 금지선의 코드 줄 가운데 측정에서 나온 것은 "지키는 것" 절의 표에 있고, 리뷰 줄(`review/`)은 아직 측정 전이다.

## 리뷰 절차

1. **범위를 정한다.** PR 번호가 있으면 그 PR, 없으면 현재 브랜치와 기본 브랜치의 갈림점(`git merge-base`)부터 지금까지다. 범위가 모호하면 사용자에게 확인한다.
2. **맥락을 모은다.** `node <이 스킬 폴더>/scripts/context.mjs`를 돌린다. PR이면 `gh pr checkout 번호`로 체크아웃한 뒤 `--pr 번호`를 붙이고, 기준이 기본 브랜치가 아니면 `--base 브랜치`를 붙인다. 요약은 표준 출력으로 나오고, 전체는 `docs/gimi/reviews/`의 JSON에 쓰인다. 요약의 "건너뜀"에 있는 맥락은 직접 모으거나, 모으지 못했다고 보고에 적는다.
   - **계약** — 요약의 "계약"은 바뀐 OpenAPI·GraphQL 계약마다 바뀐 엔드포인트·필드와 등급(깨질 수 있음·확인·추가)을 보인다. GraphQL은 그 필드를 고르는 연산(`연산 이름 › 필드 경로`)을, OpenAPI는 그 엔드포인트의 경로 문자열(정확도 낮음)과 생성 타입의 TypeScript 참조를 사용처로 보인다. "깨질 수 있음"부터 사용처를 열어 이 변경에 맞춰 바뀌었는지 본다. "생성 타입을 다시 만들지 않았다"는 참고가 있으면 확인 질문으로 올린다.
   - **영향 범위** — 요약의 "영향 범위"는 바뀐 export(시그니처 변경·삭제·본문만 변경)와 바뀐 문자열(쿼리 키·라우트·i18n 키·저장소 키)마다 **이 변경에서 안 바뀐 사용처**를 보인다. 그 사용처를 열어 의미상 깨지는지 본다. 바뀐 export를 같은 파일의 다른 export가 부르면 "감싼 export"로 그 사용처도 보인다. 지운 줄에서 사라진 객체·타입 키는 "지운 필드"로 저장소 전체에서 이름으로 찾는다(다른 층의 화면·계약 파일·테스트 목) — 응답에서 뺀 필드를 화면이 아직 읽는지 본다. 필요하면 한 단계 더 따라간다. 문맥(앞뒤 2줄)과 함께 바뀐 사용처 목록은 JSON의 `impact`에 있다. "문자열 검색(정확도 낮음)"이라고 적혔으면 이름만 같은 다른 심볼일 수 있으니 import를 확인한다.
   - **의도·요구사항** — 요약의 PR·이슈 본문을 읽는다. Jira·Notion·Linear의 번호·링크는 연결된 도구로 본문을 읽고, 읽을 수 없으면 사용자에게 붙여 넣기를 요청한다. 요구사항을 항목으로 쪼개 diff와 하나씩 맞춰 본다.
   - **변경 이력** — 요약의 "바뀐 줄을 넣은 커밋"부터 읽는다. [수정]·[되돌리기]·[긴급]·[우회] 표시가 있는 커밋은 `git show <커밋>`으로 이유를 확인하고, 새 변경이 그 수정을 되돌리거나 건너뛰는지 본다.
3. **대조한다.** `node <이 스킬 폴더>/scripts/rules.mjs --area code,test,review`로 이 프로젝트에 맞는 규칙 목록을 본다. 설정의 `stacks`·`presets`와 회사 규칙의 "끈 프리셋 규칙"을 반영한 목록이다. diff에 닿는 규칙만 `--id ID`로 전문(왜·대신·확인·경계값·근거)을 읽고 비춰 본다.
   - 아래 겹이 위 겹을 덮는다 — 회사 규칙 > 분야 프리셋 > 공통 금지선. 회사 규칙이 끈 프리셋 규칙은 쓰지 않는다.
   - 지적에는 규칙 ID를 단다(`COM-003`·`code/empty-catch`·`SHOP-001`). 규칙이 없는 지적도 근거가 있으면 쓴다.
   - `review/` 줄은 리뷰를 쓰기 전에 스스로 확인한다(diff 안에서만 판단·근거 없는 지적·단정 등).
   - "참고"에 해석 값(`kcl`)이 설정되지 않았다고 나오면 그 규칙의 기간·영업일 계산은 단정하지 않고 확인 질문으로 올린다.
4. **근거가 있는 지적만 쓴다.** 형식은 아래와 같다.
5. **보고한다.** 채팅에는 지적 수와 "고쳐야 함"만 짧게 쓴다. 전체는 리뷰 기록(`docs/gimi/reviews/{날짜}-pr-{번호}.md`)에 쓴다.

## 지적 형식

```text
[고쳐야 함] 영향 범위
주문 상태 형태가 바뀌었는데 배지는 예전 형태를 읽는다

바뀐 곳  src/api/order.ts:42
         status: string → { code, label }
근거    src/components/OrderBadge.tsx:12
         status === 'PAID'  (이 PR에서 안 바뀜)
상황    결제 완료 주문 → 배지가 항상 '알 수 없음'
테스트  OrderBadge 테스트 없음
```

- 머리에는 단계(고쳐야 함·고치면 좋음·확인 질문)와 맥락 종류(영향 범위·의도·이력·슬롭·도메인 규칙)를 쓴다.
- `근거`는 diff 밖이어야 한다. 슬롭 지적만 예외로 diff 안의 줄을 근거로 쓴다. 근거를 댈 수 없는 지적은 보고하지 않는다.
- 의도를 모르면 단정하지 않는다. 티켓과 구현이 다르거나 예전 수정을 되돌린 것처럼 보이면 `확인 질문`으로 묻는다. "무엇이 어긋나 보이는가 + 의도했다면 무엇을 알려 달라"를 쓴다.

## 지키는 것

- 사용처를 찾지 못한 것과 찾기를 건너뛴 것을 구분한다.
- 린터·포매터가 잡을 취향은 지적하지 않는다.
- 칭찬과 diff를 다시 설명하는 요약을 쓰지 않는다.
- 같은 문제는 한 지적으로 묶고 위치를 나열한다.
- 돌려 보지 않은 결과를 단정하지 않는다. 돌렸으면 명령과 결과를, 아니면 추정이라고 적는다.

측정에서 gimi 없이 한 번 이상 나온 줄이다. 코드 줄(`code/`)은 기능 구현·테스트 작성 요청 12개를 gimi 없이·있이 2번씩 실행해 셌고, diff에서 먼저 찾는다. 리뷰 줄(`review/`)은 PR 12개를 내장 `/code-review`(gimi 없이)와 gimi-review(gimi 있이)로 2번씩 리뷰해 셌고, 리뷰를 쓰기 전에 스스로 확인한다.

## 처음 설정

회사 저장소에서 "도메인 규칙 설정해줘"라고 하면 다음을 한다.

1. 분야 프리셋을 고른다(여러 개 가능 — 지금은 `commerce`·`kr-commerce-law`). 국내 법령 프리셋은 법률 자문이 아니라고 알리고, 해석 값(`kcl.periodCounting`·`kcl.businessDays`)을 팀이 정하게 한다.
2. 요구사항 출처(GitHub PR·이슈, Jira, Notion·Confluence, Linear)를 고른다.
3. 코드에서 도메인 규칙 초안(enum·union 타입, 상태 전이 함수, 검증 스키마, 금액·날짜 계산)을 뽑아 `docs/gimi/candidates.md`에 후보로 쓴다.
4. 사람이 승인한 후보만 `docs/gimi/rules.md`로 옮긴다.
5. 고른 값을 `.agents/gimi.json`에 쓴다.

같은 종류의 지적이 리뷰 기록에 세 번 쌓이면 규칙 후보로 올린다. 사람이 승인해야 규칙이 된다.

## 쓰지 않는 경우·한계

- 무엇이 바뀌었는지 설명만 원하는 요청, 보안만 보는 검토, 코드 단순화에는 쓰지 않는다.
- 테스트를 쓰거나 끝내기 전에 테스트를 돌리는 일은 gimi-test의 몫이다.
- 맥락은 같은 저장소 안에서만 모은다. 프론트와 백엔드가 다른 저장소면 계약 파일(OpenAPI·GraphQL 스키마·공유 타입)이 들어와 있을 때만 잇는다.
