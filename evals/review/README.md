# 리뷰 평가

리뷰 품질 평가(설계 결정 15①)다. 예제 저장소(`evals/shop-fixture/`)의 결함 PR마다 `gimi-review`와 내장 `/code-review`를 같은 모델로 돌린다. 지적을 정답(`defect.json`의 `findings`)과 맞춰 기계로 채점한다.

## 명령

gimi 저장소 루트에서 돌린다. `run`은 실제 모델을 부르므로 비용이 든다.

```bash
node scripts/review-eval.mjs coverage [ID…] [--out <폴더>] [--config <파일>]
                      # 모델 없이 — 정답·근거가 gimi의 맥락 묶음(context.mjs)에 있는지
node scripts/review-eval.mjs run [ID…] --reviewer gimi|code-review --model <모델> [--runs N] [--out <폴더>] [--config <파일>]
                      # 결함 PR마다 평가용 저장소를 만들어 claude -p로 리뷰한다
node scripts/review-eval.mjs score <폴더>
                      # run이 쓴 결과를 채점표로(<폴더>/score.md) — 맨 위에 설정 조건
```

`--config`는 평가용 저장소에 넣을 설정(`.agents/gimi.json`) 파일이다. 예를 들어 분야 프리셋을 켜려면 `{ "presets": ["commerce", "kr-commerce-law"] }`를 파일로 만들어 준다. 주지 않으면 설정 없이 돈다.

`--out`을 주지 않으면 `evals/review/runs/{날짜}/`에 쓴다. 이 폴더는 `.gitignore`로 뺀다. 채점표와 해석만 `results/`에 커밋한다. `coverage --out`을 같은 폴더에 주면 `score`가 놓친 정답을 수집 실패·판단 실패로 나눈다.

## 공정하게

- 두 리뷰어는 같은 모델, 같은 덧붙인 지시(`--append-system-prompt`)를 받는다. gimi만 `--plugin-dir`로 이 저장소를 플러그인으로 받는다.
- 사용자 설정·플러그인·MCP는 읽지 않는다(`--setting-sources project`, `--strict-mcp-config`).
- 도구는 Read·Grep·Glob·Write·Skill·Agent·Bash를 허용하고, 테스트 명령(`npm`·`npx`·`pnpm`·`yarn`)만 묻지 않고 막는다(`--disallowedTools`, `--permission-mode dontAsk`). 이어 붙인 명령은 하나라도 허용 밖이면 통째로 막힌다. code-review는 `git diff`에 따옴표 없는 `find` 패턴과 `~/.claude/CLAUDE.md` 읽기를 이어 붙여서, `Bash(git *)` 같은 명령 이름 규칙으로는 diff를 못 본다.
- 실행마다 도구 조건(`tools`)과 막힌 도구 호출(`permissionDenials`)을 결과에 남긴다. 조건이 다른 실행을 한 표에 섞을 때는 결과 문서에 적는다.
- **설정.** 평가용 저장소에는 기본으로 `.agents/gimi.json`이 없다. 설정하지 않은 사용자와 같은 조건이라, 분야 프리셋이 꺼져 있다(설계 결정 59). `--config <파일>`을 주면 그 JSON을 정상 버전(main)에 넣는다. 두 리뷰어가 같은 설정을 보고, PR diff에는 없다. 실행마다 설정(`config` — 평가용 저장소의 정상 버전에서 읽은 것)과 gimi의 규칙 목록 첫 줄(`rules` — 모델 없이 평가용 저장소에서 `rules.mjs`를 돌린 것)을 결과에 남긴다. code-review는 이 목록을 읽지 않지만, 같은 저장소라 조건을 견줄 수 있게 같은 값을 남긴다. `score`는 채점표 위에 리뷰어·조건마다 한 줄을 보이고, 조건이 다른 실행이 섞이면 알린다. 이 기록이 생기기 전의 결과는 "기록 없음"이다. `coverage`는 설정을 요약 줄에만 적고 `coverage.json`에는 남기지 않는다. `score`가 그 파일로 수집 실패를 나누므로, `coverage`는 `run`과 같은 `--config`로 돌린다.
- 평가용 저장소는 이름이 중립인 임시 폴더에 만들고, 결함 브랜치 이름은 `feature/pr`이다. 처음에 `defect/COM-024`로 만들었더니 `context.mjs`가 브랜치 이름을 티켓 번호로 읽었다.
- 결함의 `issues`는 가짜 gh(`scripts/fake-gh.mjs`)가 돌려준다. 가짜 gh는 PR이 없다고 답하므로, 맥락 묶음의 CI 결과(설계 결정 60)와 PR 본문(`intent.pr.body`)은 `github` 필드가 없는 결함에서는 돌지 않는다. 2026-11-05(설계 결정 65)부터 결함의 `github.pr`가 true면 가짜 gh가 PR #7(제목·본문은 `pr`, 닫는 이슈는 `github.closes`)과 체크(`github.checks` — 같은 저장소의 Actions 링크)를 돌려주고 `gh run view --job N --log-failed`에 그 체크의 `log`를 답한다. 두 리뷰어의 덧붙인 지시 둘째 줄이 "GitHub PR #7"로 바뀐다. `github.unavailable`이 true면 가짜 gh가 모든 명령에 로그인하지 않았다고 실패한다(맥락 수집 실패 사례). PR 제목·본문은 결함 커밋의 메시지로도 들어간다(`github.pr`가 없으면 그것으로만). 2026-11-03(설계 결정 61)부터 gimi의 요약 의도 줄에 그 커밋 메시지가 나오고 주장 확인이 그것을 본다 — 그 전 평가는 대부분 "의도 없음"이었으니 같은 조건이 아니다. 결함 PR 가운데 제목이 `refactor:`·`perf:`인 것이 많아 주장 확인과 겹치는데, 오탐을 볼 결함 없는 PR은 적다. 평가용 저장소 밖에 두고 두 리뷰어의 PATH 앞에 똑같이 넣는다. `auth status`·`issue view`·`issue list`·`repo view`·`api …/issues/N`에 답하고, `github.pr`가 없으면 PR은 없다고 답한다. `coverage`도 같은 가짜 gh로 맥락을 모은다.
- 부르는 말은 gimi가 `/gimi:gimi-review`, code-review가 `/code-review feature/pr`이다. gimi는 범위를 스스로 정한다(지금 브랜치와 기본 브랜치의 갈림점부터).

## 채점

- 리뷰어는 출력 끝에 지적마다 `FINDING <고쳐야 함|고치면 좋음|확인 질문> <경로>:<줄> <요약>`을 한 줄씩 적는다. 지적이 없으면 `FINDING 없음`을 적는다.
- 내장 `/code-review`는 이 지시를 따르지 않고 자기 JSON 지적 목록(`file`·`line`·`summary`)을 낸다. FINDING 줄이 없으면 그 목록을 읽는다. 그 목록에는 단계가 없다. 둘 다 없으면 "형식 어김"으로 센다.
- 같은 파일에서 정답 줄(범위) ±3 안이거나, 정답의 근거 위치(±3)에서 지적하면 찾은 것이다. 지적 하나는 정답 하나에만 쓴다.
- 결함 PR에서 정답에 맞지 않는 지적은 "정답 밖 지적"으로 따로 센다. 정답을 모두 적었다고 할 수 없어서 오탐으로 치지 않는다.
- 결함 없는 PR(`clean: true`)의 지적은 모두 오탐이다. 그 가운데 "고쳐야 함"을 따로 센다. 단계가 없는 지적이 섞이면 따로 세지 못한다(`-`).
- gimi는 놓친 정답을 나눈다. 정답이나 근거 가운데 하나라도 맥락 묶음에 없으면 "수집 실패", 모두 있는데 지적하지 못했으면 "판단 실패"다.
- 정답 밖 지적과 오탐은 결함 PR의 diff(`change.patch`)와 견줘 바뀐 조각(±3줄)·바뀐 파일의 조각 밖·바뀌지 않은 파일로 나눠 센다. 위치는 "이 변경에 대한 지적인가"의 대리 지표다 — 바뀐 조각 안의 지적도 원래 있던 코드를 말할 수 있고, 바뀌지 않은 파일의 지적도 이 변경으로 깨지는 곳(깨질 테스트 등)일 수 있다.

## 판정 — 위치 점수와 따로(설계 결정 65)

위치로 맞춘 "찾음"은 지적의 내용을 보지 않는다. 같은 줄의 다른 문제도 찾음이 되고, 정답과 4줄 어긋난 같은 지적은 놓침이 된다. 정답 밖 지적이 실제 결함인지도 모른다. 그래서 `score`는 결과 폴더에 판정 양식 `judgments.json`을 만들고, 사람이 내용을 읽고 판정한 것만 따로 센다.

| 항목 | 판정 값 | 뜻 |
|---|---|---|
| 위치로 찾은 정답(`found`) | 일치 · 불일치 | 지적의 원인과 실패 조건(어떤 입력에서 무엇이 잘못되는지)이 정답과 같은가. `sameLevel`은 단계가 정답과 같은지(참고) |
| 위치로 놓친 정답(`missed`) | 다른 위치에서 찾음 · 못 찾음 | 다른 줄의 지적이 같은 결함을 말했는가 |
| 정답 밖 지적(`extra`) | 실제 결함 · 잘못된 지적 · 판단 보류 · 정답과 같은 결함 | 심은 결함이 아닌 곳을 짚은 지적이 맞는가. 위치로 놓친 정답과 같은 결함을 말했으면 "정답과 같은 결함" — 그 정답은 놓친 정답 쪽에서 "다른 위치에서 찾음"으로 세어 두 번 세지 않는다 |
| 결함 없는 PR의 지적(`false`) | 실제 결함 · 잘못된 지적 · 판단 보류 | 같다 — 예제 앱에 원래 있던 결함일 수 있다 |

- 모든 항목은 `미검토`로 시작한다. 사람이 `judgment`를 바꾸고 `note`에 근거를 적는다. `score`를 다시 돌려도 적은 판정과 메모는 지키고, 새 항목만 미검토로 더한다. 판정 값에 없는 값은 알리고 미검토로 둔다.
- 사람이 적은 판정은 버리지 않는다. 채점 결과에 짝이 없는 판정과, 판정할 때의 지적(`finding`)이 지금 지적과 다른 판정은 `orphans`로 옮기고 알린다. 모양을 모르는 `judgments.json`은 덮어쓰지 않고 실패하며, 쓰기 전에 `judgments.json.bak`을 둔다. 같은 리뷰어의 같은 실행이 결과 폴더에 둘 있으면(키가 겹치면) 실패한다.
- 채점표 아래 "사람이 판정한 것" 표가 위치 점수와 따로 센다. 미검토는 아직 아무도 보지 않았다는 뜻이고, 판정한 수로 비율을 내지 않는다.
- 정답 밖 지적 수가 적다는 것만으로 오탐이 적다고 말하지 않는다 — 판정한 "잘못된 지적" 수만 오탐으로 말한다.
- 2026-11-05 전의 결과 문서(`results/`)는 이 판정 없이 쓴 것이다. 고치지 않는다. 지난 실행을 다시 판정하면 새 결과 문서에 판정한 사람·날짜와 함께 적는다.

## 실행 조건

실행마다 결과(`<리뷰어>/<ID>-<N>.json`)에 모델(`model`), gimi 판(`gimi` — 플러그인 버전·gimi 저장소 커밋·커밋하지 않은 수정이 있었는지, gimi를 받지 않은 리뷰어는 null), 도구 조건(`tools`), 결함마다 반복 횟수(`runs`), 설정(`config`)과 규칙 목록 첫 줄(`rules`)을 남긴다. `score`는 설정 조건 표 다음에 모델·gimi 판·도구·반복 표를 보인다. 2026-11-05 전의 실행은 gimi 판과 반복이 "기록 없음"이다.

실행 때의 결함 정의(`defect` — 정답)와 PR diff 조각(`hunks`)도 남기고, `score`는 그것으로 맞춘다. 2026-11-05 전의 실행에는 이것이 없어 지금 결함 정의로 맞추고, 채점표 맨 위에 그 실행 수를 알린다. 예제 앱은 2026-10-31에 바뀌어 정답 줄이 옮겨진 결함이 있다(예: `INTENT-001`의 정답이 27행 근처에서 34행으로). 그래서 그 전 실행을 지금 다시 채점하면 엉뚱한 지적이 찾음이 되거나 맞는 지적이 놓침이 될 수 있다 — 지난 결과는 그 결과 문서(`results/`)의 숫자를 쓴다.

## 판단 기준 사례(설계 결정 64·65)

설계 결정 64(근거는 diff 안팎 어디든, 실패 조건을 적고, 생긴 때를 나눔)가 다섯 경우에 맞게 도는지 볼 사례다. 2026-11-05에 4개를 새로 만들었고 나머지는 있던 결함을 쓴다. 아래 "기대 동작"은 사람이 판정할 때 쓰는 기준이지 결과가 아니다. 2026-11-10에 처음 돌렸다(리뷰어마다 1번, 결과는 `results/2026-11-10-depth.md`) — `NOCTX-001`에서 gimi가 기대와 달리 확인 질문을 내지 않았다. 설계 결정 69로 고친 뒤 같은 날 2번 다시 돌려 2번 모두 확인 질문이 나왔다(`results/2026-11-10-followups.md`).

- `PRCI-001`의 CI 로그는 결함 버전에서 예제 앱 서버 테스트를 실제로 돌린 출력(vitest)을 줄인 것이다. 처음 전체를 돌렸을 때 시간 초과로 실패한 테스트 2개(수량 0·-1)는 다시 돌리면 통과해 뺐다. 이 변경에서는 동시 주문 테스트(`server/test/orders.test.ts:35`)도 타이밍에 따라 실패할 수 있다(뒤 주문이 재고 0을 읽으면 409 대신 400). 한 번 돌린 출력이라 로그에는 없다.
- 이 사례를 돌리려면 `node scripts/review-eval.mjs run LOGIC-001 INTENDED-001 NOCTX-001 PRCI-001 IMPACT-001 CLEAN-002 --reviewer gimi --model <모델>`(유료). 결과 폴더에서 `score`를 돌리고 `judgments.json`을 판정한다.

### 안 바뀐 곳·큰 변경·다시 리뷰(설계 결정 70·71·72, 사례는 결정 74)

2026-11-11에 사례 3개를 만들었다. **아직 모델로 돌리지 않았다.** 아래 "기대 동작"은 사람이 판정할 때 쓰는 기준이지 결과가 아니다.

## 맥락 수집 점검

`coverage`는 정답과 근거마다 맥락 묶음의 어디에 있는지 본다.

| 어디 | 뜻 |
|---|---|
| 바뀐 조각 | diff 조각의 새 줄 범위 ±3 |
| 영향 범위 | 바뀐 export·문자열·계약의 사용처 ±3 |
| 바뀐 파일 | 바뀐 파일이지만 조각 밖 — 묶음이 파일을 가리키고, 리뷰어가 그 파일을 열면 보인다 |
| 지난 리뷰 | 근거가 지난 리뷰 기록 파일이고 묶음의 `prior`가 그 파일을 읽었다 — 요약의 "지난 리뷰"에 지적이 보인다(이 근거가 있는 사례가 있을 때만 집계 줄에 나온다) |
| 이력 | 근거가 커밋이면 묶음의 이력에 그 커밋이 있다 |
| 의도 | 근거가 이슈면 묶음의 의도에 그 이슈의 본문이 있다 |
| (없음) | 묶음에 없다 — 리뷰어가 스스로 찾아야 한다 |
