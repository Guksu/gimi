# gimi

Claude Code나 Codex가 코드를 리뷰할 때 쓰는 스킬입니다. 리뷰 전에 diff(이번 변경에서 바뀐 줄) 밖의 맥락을 먼저 모읍니다. 리뷰는 이 순서로 합니다.

1. 바뀐 함수·타입·문자열을 이 변경이 고치지 않은 곳에서 쓰는지 찾습니다.
2. PR·이슈 본문의 요구사항과 PR 설명의 주장을 diff와 맞춰 봅니다.
3. 바뀐 줄을 넣은 커밋을 찾아, 예전 수정을 되돌리는지 봅니다. PR이 있으면 CI 결과도 읽습니다.
4. 어떤 입력에서 무엇이 잘못되는지(실패 조건)와 근거 위치를 댈 수 있는 지적만 남깁니다.

[English](README.md) · [맞는 경우](#맞는-경우) · [설치](#설치) · [결과 읽기](#결과-읽기) · [사례](docs/cases.md) · [상세 안내](docs/guide.md) · [측정 결과](evals/review/README.md)

지적은 이런 모양입니다(설명용 예시 — 실제 실행 결과는 [사례](docs/cases.md)에 있습니다).

```text
[고쳐야 함] 영향 범위
주문 상태 형태가 바뀌었는데 배지는 예전 형태를 읽는다

바뀐 곳  src/api/order.ts:42
         status: string → { code, label }
근거    src/components/OrderBadge.tsx:12
         status === 'PAID'  (이 PR에서 안 바뀜)
상황    결제 완료 주문 → 배지가 항상 '알 수 없음'
생긴 때  이번 변경
```

예제 앱에 결함을 심은 PR 32개를 gimi와 Claude Code 내장 `/code-review`로 리뷰했습니다. 두 리뷰어는 같은 모델·같은 지시로 돌렸습니다. 결함은 둘 다 거의 다 찾았습니다(지적 위치로 센 것). 심은 결함이 아닌 곳을 짚은 지적은 `/code-review` 55개, gimi 19개였습니다. 그 지적이 틀렸다는 뜻은 아닙니다. 내용이 맞는지는 아직 판정하지 않았습니다. PR마다 한 번씩 돌렸고, gimi는 설정 파일 없이(분야 프리셋을 끄고) 돌렸습니다. 리뷰 한 번의 평균은 gimi 57초·$0.41, `/code-review` 45초·$0.31이었습니다.

요구사항이 이슈에만 적힌 결함 4개로 따로 잰 평가도 있습니다. 리뷰어마다 2번씩 돌렸습니다. 요구사항과 어긋난다고 짚은 리뷰는 gimi 8번 중 8번, `/code-review` 8번 중 5번이었습니다. 이 숫자는 지적 위치가 아니라 제가 지적 내용을 읽고 센 것입니다. [측정 방법과 전체 결과](evals/review/README.md) · [측정의 단서](docs/guide.md#측정) · [대표 사례 3개](docs/cases.md)

## 맞는 경우

- **TypeScript·JavaScript 프로젝트** — 바뀐 함수·타입을 쓰는 곳을 이 두 언어의 파일에서 찾습니다. Vue·Svelte 파일 안의 사용처는 프로젝트에 typescript가 없어 문자열 검색으로 찾을 때만 나옵니다.
- **diff 밖을 봐야 하는 PR** — gimi가 모으는 맥락은 이런 PR을 위한 것입니다.
  - 바뀐 함수·타입을 이 PR이 고치지 않은 곳에서 쓰는 경우
  - API 계약(OpenAPI·GraphQL 스키마)이 바뀐 경우. 프론트와 백엔드가 다른 저장소면 설정(`linkedRepos`)에 그 저장소 경로를 적어 둡니다. 그러면 그 저장소에서도 계약을 쓰는 곳을 찾습니다.
  - 요구사항이 이슈에 적힌 경우
  - PR 설명에 "리팩터링만"·"하위 호환" 같은 주장이 붙은 경우
  - 예전에 버그를 고치며 넣은 줄을 다시 바꾸는 경우
  - GitHub PR의 CI가 실패한 경우. PR이 없는 브랜치 리뷰에서는 CI를 보지 않습니다.
- **커머스·결제 코드** — 분야 프리셋(커머스 29개·국내 전자상거래 법령 14개)을 켜면 그 규칙으로도 봅니다.

다음 경우에는 덜 맞습니다.

- **TypeScript·JavaScript가 아닌 언어** — 다른 언어 파일이 바뀌면 바뀐 함수·타입의 사용처는 찾지 않습니다. 바뀐 문자열(쿼리 키·경로 등)의 사용처만 찾습니다.
- **테스트를 써 주거나 돌려 주기를 바랄 때** — gimi는 리뷰만 합니다. PR에 든 테스트 코드는 리뷰합니다.
- **한국어를 읽지 않는 팀** — 스킬·규칙과 지적 형식이 한국어입니다.

## 지금 상태

위 측정은 0.1.0 전(2026-10-27·10-31)에 예제 앱 한 곳에서 잰 것입니다. 그 뒤에 더하고 바꾼 것은 아직 재지 않았습니다. 예를 들면 이런 것입니다.

- PR의 CI 결과를 지적의 근거로 쓰는 것
- PR 설명과 커밋 메시지의 주장을 모은 맥락과 맞춰 보는 것
- 같은 지적이 여러 리뷰에서 되풀이되면 세어 규칙 후보로 올리는 것
- 설정이 없을 때 프론트엔드·백엔드 중 무엇을 볼지 저장소를 보고 정하는 것
- 다른 저장소에서 계약을 쓰는 곳을 찾는 것(`linkedRepos`)
- 리뷰 절차(SKILL.md)를 줄여 다시 쓴 것

분야 프리셋을 켰을 때의 효과도 재지 않았습니다. 예제 앱 밖의 실제 저장소에서 잰 결과는 아직 없습니다.

2026-11-10에 지금 판으로 같은 결함 32개를 한 번씩 다시 돌렸습니다. 위치 기준으로 찾은 수는 전과 같았습니다(31/32). 결함 없는 PR 6개에는 지적이 없었습니다. 다만 위 변경들이 한꺼번에 들어간 뒤의 결과라, 변경마다의 효과는 가르지 못했습니다. gh 없이 요구사항을 읽지 못한 사례 하나는 기대(확인 질문으로 묻기)대로 돌지 않았습니다. [결과](evals/review/results/2026-11-10-depth.md)

## 설치

**Claude Code** — 대화창에서 실행합니다.

```text
/plugin marketplace add Guksu/gimi
/plugin install gimi@gimi
```

**Codex** — 터미널에서 실행합니다.

```bash
codex plugin marketplace add Guksu/gimi
codex plugin add gimi@gimi
```

Node.js 22 이상과 리뷰할 git 저장소가 필요합니다. PR·이슈 본문을 읽으려면 GitHub CLI(`gh`)에 로그인해 둡니다.

[필요한 것](docs/guide.md#설치) · [업데이트](docs/guide.md#업데이트)

## 첫 요청

설치한 뒤 리뷰할 저장소에서 이렇게 요청합니다.

> gimi-review로 지금 브랜치를 리뷰해줘. 바뀐 API를 쓰는 화면이 깨지지 않는지, 이슈의 요구사항대로 됐는지도 봐줘.

에이전트는 리뷰 전에 바뀐 코드를 쓰는 곳, PR·이슈 본문, PR의 CI 결과, 바뀐 줄의 이력을 모읍니다. 그다음 근거 위치를 댈 수 있는 지적만 남깁니다. 전체는 `docs/gimi/reviews/`에 기록합니다. Claude Code에서는 `/gimi:gimi-review`로 직접 부를 수도 있습니다. 스킬과 규칙 문서는 한국어로 작성되어 있습니다.

커밋하기 전의 변경을 보려면 "커밋하기 전에 방금 고친 코드 리뷰해줘"처럼 요청합니다. 커밋하지 않은 변경과 새 파일을 함께 봅니다.

커머스·국내 전자상거래 법령 규칙으로도 보려면 "도메인 규칙 설정해줘"라고 요청합니다. [설정](docs/guide.md#설정)

## 결과 읽기

- **채팅** — 첫 줄에 결론(단계마다 지적 수와 건너뛴 맥락)이, 그 아래 "고쳐야 함"과 "확인 질문"이 한 줄씩 보입니다. "고치면 좋음"은 수만 보입니다.
- **파일** — 리뷰한 저장소에 두 파일이 생깁니다. PR에 코멘트를 달거나 GitHub에 무엇을 올리지는 않습니다.
  - `docs/gimi/reviews/{날짜}-pr-{번호}.md`(PR이 없으면 `{날짜}-{브랜치}.md`) — 리뷰 기록. 지적마다 단계·근거·상황·생긴 때·규칙·판정을 적습니다.
  - 같은 이름의 `.context.json` — 모은 맥락 전체. 크고 다시 만들 수 있어 커밋하지 않습니다. `.gitignore`에 `docs/gimi/reviews/*.context.json`을 더합니다.
- **건너뛴 맥락** — 맥락 수집 요약과 리뷰 기록에 모으지 못한 맥락과 이유가 "건너뜀"으로 나옵니다. 그 부분은 리뷰가 보지 못한 것입니다. "지적 없음"이어도 건너뛴 맥락이 있으면 그 부분은 확인되지 않았다고 읽어 주세요. "사용처 없음"(찾았는데 없음)과 "건너뜀"(찾지 못함)은 다릅니다.

| 없을 때 | 달라지는 것 |
|---|---|
| `gh` 로그인 | PR·이슈 본문과 CI 결과를 읽지 않고 건너뜀으로 적습니다. 의도는 커밋 메시지로만 봅니다 |
| 리뷰할 프로젝트의 `typescript` | 바뀐 이름의 사용처를 문자열 검색으로 찾고 "정확도 낮음"으로 표시합니다. 이름만 같은 다른 코드가 섞일 수 있습니다. `node_modules`에 git이 추적하는 파일이 있을 때도 같습니다. 보안 때문에 typescript를 불러오지 않습니다 |
| 전체 이력(얕은 복제) | 변경 이력을 건너뜁니다. `git fetch --unshallow` 뒤 다시 돌립니다 |
| Jira·Notion·Linear 연결 | 그 티켓을 읽지 못하면 본문을 붙여 넣어 달라고 묻습니다 |
